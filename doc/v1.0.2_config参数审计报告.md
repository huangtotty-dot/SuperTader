### 0.2 死键的来源（为什么积累到 75%）

死键不是乱写的，是**迭代埋的坟**：V2 评分引擎重写（07-23）把"参数化阈值"改成了"sigmoid 归一化 + ATR 自适应 + 硬编码中心值"，V1.11-V1.26 各代因子的参数键随之失去消费端；v1.0.1/v1.0.2 清理了代码实体（因子函数、状态机）但**没有同步清理 config**。典型模式有三类：

1. **阈值硬编码化**：`rsi_overbought/rsi_oversold` 的评分端已硬编码 78/35（signal_engine.py:1066/1072）；双顶保护 5 个阈值键全部硬编码（:757-768）。
2. **机制整体删除**：确认型收敛（buy_confirm_*）、防饿死（buy_starvation_*）、尾盘强平（force_close_*，main.py:1374 注释"用户反馈不需要"）、纠正引擎（CORRECTION_PARAMS 从未接入 V2）。
3. **字典从未接线**：ETF_T0_PARAMS 定义后从未被 import 或传入（position_sizer.py:37-38 期望它在传入的 params 里，main.py:1294/1303 传的合并 dict 不含它）。

## 1. 【先修后删】4 处参数接线断线（P0，比精简更重要）

这些不是冗余——参数本身是精心调优的，但消费端读错了地方，**当前全部空转**：

### N1. TrendRegime 未接 PARAMS —— v1.0.2 新增的 5 个趋势层键是死键

- 实锤：signal_engine.py:466 `self.trend_regimes[code] = TrendRegime()` 无参实例化，永远使用 trend_regime.py:32-42 的 DEFAULT_PARAMS。
- 影响：`rsi_period_5m / rsi_oversold_5m / rsi_overbought_5m / trend_bb_slope_flat / trend_bb_width_expand / trend_debounce_bars` 写进 config 但**改它们没有任何效果**，也无法做个股差异化（如华工科技 5分钟 RSI 超买想设 72）。
- 修法：`TrendRegime(params=_sp_param 合并后的 dict)`，与个股参数体系打通。

### N2. take_profit_pct / take_profit_time_after —— 全部 Optuna 寻优结果空转

- 实锤：这两个键**只存在于 STOCK_PARAMS**（config.py:576/614/651/678/704，5 只标的 0.0148~0.0212），而 signal_engine.py:148/283/590 用 `PARAMS.get("take_profit_pct", 0.010)` 读——PARAMS 里没有这个键，**永远走默认 0.010**。
- 影响：5 只标的的 Optuna 100trial 寻优止盈值从未生效一天。
- 修法：改 `_sp_param(code, "take_profit_pct", 0.010)`。

### N3. vwap_buy_deviation —— 6 只标的的 VWAP 偏离阈值空转

- 实锤：signal_engine.py:513 只读 PARAMS（无此键），STOCK_PARAMS 里各股的 -0.0161~-0.0313 从未生效，永远走默认 -0.020。
- 修法：同 N2，改 `_sp_param`。

### N4. bullish_reversal_* 个股参数从不传入

- 实锤：`extract_5min_features(bullish_params=None)`（signal_engine.py:833），唯一调用点 :744 从不传参，永远用函数内默认值。300153/600481/000988 的 V1.24 反包调优（min_pct/body_ratio/vol_multiplier）从未生效。
- 修法：调用点按 code 从 STOCK_PARAMS 取参传入。

### 附带发现（非 config 问题，顺带登记）

- `send_morning_alert` / `notify_alert_cleared`（main.py:309/347）**全工程无调用方**——早盘预警只拦买不推飞书，用户收不到红色预警卡片。
- main.py:1215 读 `last_stand_down_reason`、main.py:191 读 `open_dip_reason`——V2 引擎已不产出这两个字段，面板显示为死代码。
- MORNING_ALERT_PARAMS 中 300364 的 3 条规则含 `consecutive_bearish` 条件键，`_check_morning_alert` 的 locals() 无此变量 → 永不命中（v1.0.2 清死键时漏了它）。

## 3. 精简方案（三级）

### 级别一：安全删除（零风险，建议立即执行）

- PARAMS 160 死键（含 min_profit_space 重复行）
- CORRECTION_PARAMS 整段
- STOCK_PARAMS 死键（除第 1 节"修复后保留"的 4 组）
- MORNING_ALERT_PARAMS 死键与 3 条死规则
- SENTIMENT_PARAMS 3 个执行层死键
- INDEX_INTRADAY_PARAMS 整段（与默认全同值）
- INDEX_REGIME_PARAMS 97 个同值键

**效果：config.py 从 1350 行瘦身至约 600-650 行，PARAMS 从 214 键降至 54 键。** 所有删除项均有"零消费"grep 证据，不改变任何运行时行为。

### 级别二：修复后归位（先做第 1 节 N1-N4，再决定保留）

- trend_*/rsi_*_5m 5 键 → TrendRegime 接参后保留（并支持 STOCK_PARAMS 个股覆盖）
- take_profit_pct/time_after、vwap_buy_deviation、bullish_reversal_* → 改 `_sp_param` 后保留
- ETF_T0_PARAMS → 删除整段，但先把 ETF 专属的份数/倍率参数显式并入 STOCK_PARAMS["588170"]，消除"恰好等于默认值"的隐性依赖

### 级别三：需用户拍板（有语义分歧，不擅自删）

1. **t_matrix["uni_down|ice"] 方向反转**：config 覆盖值是 `["short", 1.0, ...]`（config.py:1333），模块默认是 `["long", 0.3, ...]`（daily_sentiment.py:229）——**两者方向相反**。这是活跃覆盖且影响 T 模式决策，是有意为之还是误配？需确认后保留或修正。
2. **1分钟 RSI/BOLL/EMA 周期键**（rsi_period/bb_period/bb_std/ema_fast/slow）：当前仍被 indicators.py/data_fetcher.py 消费（算 1分钟指标列喂给权重 0.04-0.08 的因子）。若后续按方案把 1分钟 RSI 因子彻底下线，这组键可一并删除——**建议暂留**，待 90 日 A/B 回测决定 1分钟因子去留。
3. **awaiting_buyback_vwap_gap / morning_no_sell_until / morning_no_sell_min_ret**：全局键活跃，但个股覆盖无效（消费端只读 PARAMS）。若希望个股差异化（如 588170 的 0.995 接回 gap），需先改 `_sp_param` 再保留个股键；否则删除个股副本保留全局键。

## 4. 执行建议与验收

**推荐顺序**：先做第 1 节 N1-N4 断线修复（这些直接影响信号正确性，比删键重要）→ 再执行级别一安全删除 → 拍板级别三。

**验收方法**：
1. 断线修复后：对 300153 回放验证 take_profit_pct=0.0148 真实生效（止盈触发价与调优值一致）；TrendRegime 传入 params 后改 rsi_oversold_5m 观察 trigger 变化。
2. 删键后：全量 import 冒烟（`python smoke_test_v101.py`）+ replay_day 场景日回放，逐信号对照删键前后输出**应完全一致**（死键删除是无行为变更重构）。
3. 删键清单执行前建议 `git commit` 打快照，删除单独一个 commit 便于回滚。

**长期治理建议**（防止再次积累）：
- 参数入 config 的前置条件：消费端必须先上线（不允许"先配参数后接代码"）。
- 每轮删因子代码时同步删参数（把"config 清理"列入因子下线 checklist）。
- 可在 smoke_test 中加一项"PARAMS 键消费率"静态检查，低于阈值时告警。
