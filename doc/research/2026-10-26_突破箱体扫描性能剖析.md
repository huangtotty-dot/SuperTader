# 突破箱体扫描：性能剖析与优化方案（2026-10-26）

> owner 报「运行箱体突破后发现有卡顿」。
> 本文只做**测量与定位**；改动尚未落地（见文末「落地状态」）。

## 1. 实测：全池 5400 只，缓存路径 ≈ 97 秒

GM 未连接时走本地缓存路径（`_gm_off=True`），用 `tmp/bk_bench.py` 分段计时：

| 阶段 | 耗时 | 单只 | 备注 |
|---|---:|---:|---|
| ① 末根日期 `_bk_cache_last` × 5400 | **23.4 s** | 4.33 ms | 每只把 53KB 的 JSON 全解析一遍 |
| ② 建帧 + 判定 × 3073 | **73.8 s** | 24.0 ms | 其中 `_tdx_df` 33.3 s、`_detect_boxes` ≈16 s |
| 合计 | **97.2 s** | | |

cProfile（同一负载，含剖析开销 134 s）前几名：

```
cumtime  调用     函数
 60.2s   3070   _breakout_probe_one
 49.8s   3073   _bk_cached_df          ← 其中 _tdx_df 33.3s
 40.7s   3051   _box_top_for → _detect_boxes
 29.0s   8473   _load_json             ← 23.9s 花在 json.loads
 24.4s   5400   _bk_cache_last         ← 里面同时做了 json + parquet
 13.0s   8431   pyarrow.read_row_group
```

**普通交易日的实际组合不同**：如果猎手当天把 `daily_kline` 缓存更新到了目标日，
② 里就不会走 `_tdx_df`（那一档 33 s 会消失）；反之若缓存停在上一交易日、
通达信 parquet 也没目标日，则全部在 ① 就被判 stale。

⚠️ **绝对值随机器负载大幅漂移**：同一份代码在机器空闲时量到 4.33 + 24.0 ms/只，
在另一个会话跑重活时（同时有 python 进程占着 ~2.5 核）量到 11.7 + 43.5 ms/只，
差 2 倍。所以**优化前后必须背靠背测**，别拿今天下午的数跟昨天晚上的数比。
`tmp/bk_bench.py` 默认跑两轮并只认**最后一轮**，就是为了压掉磁盘冷缓存。

## 2. 三处纯浪费（与算法无关）

### ① 为了拿「末根日期」把 53KB 的 rows 全解析

`daily_kline/{code}.json` 的**顶层 `date` 字段**就是缓存截止日，位于文件前 ~30 字节：

```json
{"date": "2026-10-20", "saved_at": "...", "rows": [ ... ]}
```

实测（300 只）：全量 `json.load` **6.2 ms/只**，只读前 256 字节 **0.48 ms/只**，快 13×。

⚠️ **不能直接拿顶层 date 当 rows[-1].date**：抽样 1200 只，1173 只相等，
27 只（2.3%）顶层**更新**——都是停牌/退市票（例：`000024` 顶层 2026-08-07、末根 2015-12-07）。
所以顶层 date 只能当**上界**用：
- `顶层 < 目标日` ⇒ 一定缺目标日（可安全跳过，不用解析 rows）；
- `顶层 ≥ 目标日` ⇒ 仍需解析 rows 才能确定末根。

### ② 每只票都读一次 parquet row group，只为拿末根日期

`_tdx_last()` 现在是 `pf.read_row_group(rg, columns=["date"])`，**1.37 ms/只**，
全池 5400 只 = **7.4 s**。

但 parquet 的 row-group 元数据里**已经存了每组的 `date` min/max**：
建一次 `code → (row_group, 最大日期)`（9506 组，**0.36 s**，按 mtime 缓存），
之后查表 **0.0005 ms** —— 快 **2709 倍**。

### ③ 同一个文件被解析两遍

`_bk_cache_last()` 解析 JSON 拿到末根日期后，`_bk_cached_df()` **又解析了同一个文件**
（3032 只 × 3.4 ms ≈ **10 s** 白扔）；而且这 3032 只最后还走了 `_tdx_df`
（再来一次 parquet 读 + `to_pandas`，33 s），可它们的 JSON 明明已经知道缺目标日。

## 3. 排除掉的怀疑

- **ArrowDtype 不是瓶颈**：`to_pandas()` 出来的是 pyarrow-backed 列（`str`/`float32`），
  但换成 numpy `float64` 后 `_detect_boxes` 只快 **4%**（1.629 s → 1.565 s / 300 次）。
- **`_detect_boxes` 本身已向量化**：5.2 ms/只，在一次 24 ms 的循环里只占两成；
  再压它就得改分位数口径（88/12 会随之变化），**会改变信号，不做**。

## 4. 优化方案（待落地）

| # | 改动 | 预计省 |
|---|---|---:|
| 1 | `_tdx_last` 改走 parquet 元数据查表（`_tdx_index` 顺手存每组 date 最大值） | ≈7.4 s |
| 2 | `_bk_cache_last` 只读文件头拿顶层 date，**只有日期够新才全量解析** | ≈18 s |
| 3 | 合并 ①③：一次读盘拿到 `(df, kind)`，`_bk_cached_df` 不再重复解析 | ≈10 s |
| 4 | 元数据先比日期：通达信整体没有目标日时**一次都不读 row group** | ≈33 s（本场景） |
| 5 | 每 50 只让出一次 GIL（`sleep(5ms)`），主力线程不被连续占死 | 卡顿改善 |

预计：**97 s → ≈28 s**（本场景）；若通达信真有目标日数据，约 **61 s**。

### 原型已实测（`tmp/bk_proto.py`，不改仓库代码）

把上面 1~4 条在独立脚本里实现一遍，和现状**背靠背跑同一批 400 只**：

| | ①+② 合计 | 命中 |
|---|---:|---:|
| 现状 | 18.31 s | 1 |
| 原型 | **3.68 s**（索引构建另计 0.60 s，一次性） | 1 |

**5.0× 提速，命中完全一致**（集合差为空）。取值分布 `json=217 / stale=183`：
那 183 只在现状里要付「全量 JSON 解析 + 一次 parquet row group 读」才被判 stale，
原型只花一次 256 字节的文件头读 + 一次元数据查表。

## 5. 落地结果（2026-10-26，重构提交后）

改动只碰**取数路径**，判定口径（`_detect_boxes` / 箱体上沿 / 幅度闸 / 当日涨幅闸）一行没动：

| 位置 | 改动 |
|---|---|
| `t_gui.Api._tdx_index` | 建索引时顺手记下每个 row group 的 **date 最大值**（同一份元数据，几乎零成本）；date 列按**名字**定位，不写死列号 |
| `t_gui.Api._tdx_last` | 改查表：`read_row_group` → `dict` 查表 |
| `t_gui.Api._bk_head_date` | 新增：**只读文件头 256 字节**拿顶层 `date` |
| `t_gui.Api._bk_cache_last` | 增加 `target` 参数；日期改从文件头取；文件头够新时**完全不碰通达信** |
| `core/scanners._scan_breakout` | 把 `dt_target` 传给 `cache_last`；每 64 只 `sleep(3ms)` 让出 GIL |

### 实测（`tmp/bk_ab.py`，同一批 800 只、同一天、完整 `_scan_breakout`、强制只走缓存）

```
旧 A:  15.38s  命中 2  ok 413  stale 387  no_data 0  cached 413
新 B:   7.28s  命中 2  ok 413  stale 387  no_data 0  cached 413
命中集合一致 ✅   统计口径一致 ✅   提速 2.1x
（外推全池 5400 只：104s → 49s）
```

分段看（`tmp/bk_bench.py`，600 只，热轮）：`① 末根日期` **3.41 → 0.30 ms/只（11x）**。

## 6. 还剩什么（没动的部分）

每只「当日有 bar」的票仍要付：`json.loads` **5.6 ms** + `pd.DataFrame` **2.4 ms**
+ `_detect_boxes` **5.2 ms** ≈ 13 ms。这部分是**算法本身**，再压只有两条路，都有代价：

- 换更快的 JSON 解析器（本机没装 `orjson/ujson/msgspec`，装了能省 ~4 ms/只）；
- 把 `_detect_boxes` 改成纯 numpy 入参、并换掉 `np.percentile` 的插值口径 ——
  **会改变箱体上沿 ⇒ 改变信号**，不做。

## 7. 三个既有测试失败与本改动无关（日期腐烂）

`tests/phase3/test_breakout_daily_breakout.py` 的
`TestScanFetchFailure::test_整池无帧判取数失败 / test_有帧但无当日bar判取数失败 /
test_北交所缺帧不误判为非北交所失败` 是**注入假 provider + 目标日 2026-10-09**。
但 2026-10-25 起扫描开跑前会用真实缓存探测覆盖率，本地缓存早就覆盖 10-09 ⇒
`_gm_off=True`，假 provider 根本不会被调用 ⇒ 用例语义失效。

实测（`tmp/bk_failcheck.py`）：真实覆盖率 = 100%；把覆盖率强制成 0（走 GM 路径）后
`stale=1 / fetch_failed=True`，与用例期望一致。**属既有日期腐烂，不是本次改动引入。**
