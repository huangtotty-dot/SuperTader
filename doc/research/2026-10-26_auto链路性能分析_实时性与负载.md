## 1. 延迟链拆解（行情到达 → 下单/推送）

**驱动模型：纯事件驱动，无轮询主循环。** `subscribe(symbols=18只, frequency="60s", count=240)`（gm_main.py:751-753），GM SDK 每分钟推一批 60s bar → `on_bar`。无 tick 订阅。所有策略动作是 `hooks.on_bar`（hooks.py:829-897）里的**每日一次时点钩子**：09:31 预筛 / 10:00 早盘卖→买 / 10:08、10:14 补单 / 14:50 止损到期。bar 间隙（如 09:32~09:59）每分钟 on_bar 只做：watcher 心跳 stat + 心跳写盘 + （有挂单时）对账轮询。

### 各环节耗时定性/实测

| 环节 | 路径 | 耗时 |
|---|---|---|
| 行情到达→钩子触发 | 60s bar 推送 → on_bar → 时间窗判断 | ≤1 个 bar 周期（时点都选在 bar 边界上，实测≈秒级） |
| **09:31 盘前预筛** | `prepare`（hooks.py:165）→ `prescreen.premarket_candidates`（prescreen.py:155）→ 全市场 ~5000 只 × 40 根日线，**25 批 × 200 只串行 GM history**（prescreen.py:45/189-193，facade.py:324-353） | **实测 169.0s~472.5s，最差 1344.5s（10-15）**，跑在 on_bar 线程内，**全程阻塞 SDK 事件派发** |
| 10:00 买侧取数 | `history(1800s)` 单次批量 ~300 候选（hooks.py:260-263） | 单次调用，秒级（实测定量缺，存疑，估 1~5s） |
| 决策核 | `decision.evaluate` 纯 Python 四闸门（decision.py:93-224），≤400 候选 | <0.1s，可忽略 |
| 下单 | 逐票 `order_volume`（gateway.py:179-184），经单 worker 线程池 + 15s 硬超时（gm_main.py:181-197）；`_place_and_poll` 理论最多 sleep 3×2s/票（executor.py:195-208），但 GM 仿真同步回报 order_id 恒空 ⇒ 轮询前置条件不成立，实际不 sleep | 每票约 0.1~0.5s（存疑，未实测单笔） |
| 委托→成交回报 | 实测 10-23 两笔卖单：order 14:50:01.69/01.73 → fill 事件 14:50:07.76/07.78 | **≈6.1s**（GM 仿真撮合 + 异步回调 + 落盘） |
| 成交→OSC 账本回填 | `on_order_status` 内同步调 `fillbackfill.apply_fill`（gm_main.py:1186-1194），每次全量扫 journal + 读写 positions.json/fills json（fillbackfill.py:101-120/274+） | 每笔 fill 6~10 次文件 IO，同步在回调线程；日均 ≤10 笔，量级可接受 |
| 成交→飞书推送 | 事件桥 jsonl → watcher 独立进程 tail（2s 轮询，watcher.py:475）→ 同步 urllib POST（feishu.py:74-94） | 正常 ≈3~9s；失败重试最坏 ~51s（15s×3 + 2s/4s 退避）但**只在 watcher 进程内，不碰交易线程** |

**结论：正常交易日端到端「10:00 bar → 委托发出」≈ 数秒级，瓶颈不在决策而在①盘前预筛的 3~22 分钟 on_bar 阻塞、②SDK 单 worker 串行化。**

## 3. 文件 IO 频率盘点（有没有每 tick 写盘？）

**没有每 tick 写盘**（无 tick 订阅）。每 bar（每分钟）固定写盘：

- heartbeat.json 覆写 + heartbeat_YYYYMMDD.jsonl 追加（writer.py:225-227，经 gm_main.py:1040）——每分钟 2 写，仅 MODE_LIVE；
- watcher 自心跳每 2s 覆写 watcher_heartbeat.json（watcher.py:478-487）——独立进程；
- 事件类（order/fill/reject/risk/audit）按事件追加，日均数十条，audit 双写 + flush（gm_main.py:439-459）；
- 账本/留痕（positions.json / fills / sells / day_state / decision json）只在钩子时点写，均 tmp+replace 原子写（hooks.py:110-126、fillbackfill.py:84-90），设计健康。

IO 总量：**不构成负载问题**。唯一值得注意的是 H4 的每分钟 2 次 SDK 调用（不是磁盘问题，是 SDK 池占用问题）。

## 4. 推送链路（飞书）

- **策略进程从不直接发飞书**（execution/auto 内 grep 仅 watcher.py/feishu.py 命中）。策略只写事件桥文件；watcher 独立进程 tail + 推送（watcher.py:442-475）。
- feishu.py:74-94：同步 urllib，15s 超时，网络类异常最多 3 次（退避 2s/4s），业务错误（code≠0）不重试——**最坏 ~51s 全在 watcher 线程内，绝不卡决策循环**。✅ 架构达标。
- 已知短板（非性能）：watcher 未走 ops_guard 落盘时 stdout 不可观测（watcher.py:149-164 注释自述）；`_push` 失败仅落 pushes jsonl，无二次升级通道。

## 5. 进程健壮性（顺带）：吞异常/静默死亡模式

| 位置 | 模式 | 风险 |
|---|---|---|
| hooks.py:836/851/865/882/893 | **每日一次标记在钩子执行前置 True**，钩子抛异常 ⇒ 当日该动作永久跳过不重试。`try_sell` 异常 ⇒ **14:50 卖侧当日缺席**——与历史上「14:55 尾盘归位未执行」同型。预筛失败是 fail-closed 设计（合理），但**卖侧/补单轮缺重试**是真实缺口 | 高（卖侧是风控腿）。建议：卖侧钩子失败则下一根 bar 重试（标记后置或加 retry 计数） |
| gm_main.py:835-856（`_safe_log`） | 两级兜底后整条吞掉，日志行丢失无任何痕迹 | 低-中（10-14 GBK 事故的解药，但副作用是"日志静默缺失"不可观测；TeeStream 落盘那半仍在，ops_guard.py:192-210，实际缓解到位） |
| gm_main.py:116-117/125-126/168-171/378-379/1038-1039 等 | 大量 `except Exception: pass` | 多数有注释说明且 fail-open 合理；`_get_holding` 对账失败静默（378-379）会让台账残影拖到下一 30min 窗口，属已知取舍 |
| fillbackfill / executor 各写盘 | 失败仅 log 一行，不阻断 | 符合"落盘失败不拖垮主循环"纪律；但 sell 侧账本失真时依赖卖前 reconcile_book 兜底（hooks.py:760-773），链条自洽 |
| gm_main.py:86-95（atexit banner）+ watcher 600s 心跳 | 优雅退出有 banner，硬 kill 靠 watcher 心跳告警兜底 | ✅ 覆盖了「静默死亡无 traceback」；但 H1 阻塞会造成**假阳性**心跳告警（见 H1 实测），告警信噪比受损 |

## 6. 优先建议（按性价比排序）

1. **H1 预筛前移/异步化**（收益最大：消除每日 3~22min 事件线程阻塞 + 误报告警 + 越窗风险；预筛数据与盘中行情无关，前移到 init 完全等价）。
2. **H4 心跳账户查询降频**（480→~100 次 SDK 调用/日，释放单 worker 池）。
3. **卖侧钩子失败重试**（健壮性，堵「14:50 未执行」同型缺口）。
4. H2 批大小对齐 900（一行常量，174s→~50s；若 H1 落地则降为锦上添花）。
5. H5/H7 内存缓存（顺手项）。
