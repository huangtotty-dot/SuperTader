## 0. 口径澄清（与任务背景的两处出入，必须先对齐再施工）

勘探实验代码后确认两处与背景描述不符之处，本方案以代码为准：

1. **z 值不是横截面，是逐票时序 z。** `gp_miner._zscore_matrix` 即 `fast_zscore`
   （`t_io/validation/factor_mining/gp_miner.py:88-116`，别名在 119 行）：
   对**单票** (n_days, L) 因子矩阵，在每一列（日内时刻）上用**过去 14 个交易日同刻**
   的值做 z = (今 − 均值)/标准差（ddof=1），严格因果不含当日，最小历史 5 日
   （`Z_LOOK, Z_MIN_HIST = 14, 5`，gp_miner.py:75）。实验调用点
   `run_b7_factor_filter.py:175` 对每票面板独立求 Z，**不存在跨票横截面步骤**。
2. **没有 5 倍 MAD 裁剪。** 参数 "5" 是 `min_hist=5`（最小历史日数门控，
   gp_miner.py:111 `day_ok`），全代码库 grep 无 MAD 实现。

**结论：生产不需要「当日全部候选票横截面面板」，每票只需要自己过去 14 个交易日的
14:30 因子标量。** 这把数据链路从「横截面面板工程」降级为「每票每日一个标量的持久化」，
是本项目最大的复杂度减法。

### 1.2 已有/没有的计算能力

- **没有**任何盘中 z 值或因子计算能力（core/ 与 execution/ 全 grep 无 zscore 实现；config.py:976 的 z_score 是大盘情绪 z_S，与本因子无关）。
- **有**当日分钟 bar 全字段（amount/volume 在 bar_cache 行内，gm_main.py:2698-2699）→ vwap = cumsum(amount)/cumsum(volume) 可就地计算，与实验 `build_stock_panel` 的 vwap 构造（gp_miner.py:371-376）同式。
- **没有**跨日分钟面板持久化；bar_cache 480 根封顶只覆盖约 2 天 → z 所需的 14 日历史必须新建持久化。
- 分钟快照 `t_io/minute_snapshots/` 由 manual 链 `main.py:2185`（`core/utils.py:_snapshot_write` :108）写，9 月仅覆盖约 10 票且非每日 → **不能作为 auto 池全票的 z 历史来源**。

### 1.3 因子在 14:30 列的数据依赖深度（因果审计）

`F(14:30) = ts_min_w30(ts_delay_w20(tail30_ret(vwap)))`，逐日切片内沿 bar 轴滚动
（gp_ops.py:230-241 `tail30_ret` = c[i]/c[i−30]−1；:108-110 `ts_delay` 右移 20；
:92-94 `ts_min` 30 根滚动最小）：

- 14:30 列（全日第 ~210 根，gm 终点标签口径）最深回看到 vwap[t−49−30] ≈ 13:11 的 bar；
- **全部输入 ≤ 14:30 bar，无任何未来数据**；
- 重要推论：**在 14:55 用 bar_cache 中「时间 ≤14:30 的当日 bar 切片」计算 F(14:30)，与 14:30 当场计算逐点等价**。这是 §3 推荐惰性计算方案的依据。

## 2. 总体设计（已按施工实际落点更新）

新增一个独立纯逻辑模块 + 两处 gm_main 挂钩 + 一个参数开关 + 一份历史文件：

```
core/b7_factor_filter.py                  # ★生产模块（纯 numpy+标准库，不 import gm.api，
                                          #  自测 27 断言；owner 施工口径落 core/ 而非 execution/auto/）
t_io/state/b7ff_factor_hist.json          # 因子历史：{code: [{date, f}]}（bootstrap 已回填）
execution/auto/_gm/config/params.py       # b7_factor_filter_enabled 开关（§5，默认 False）
execution/auto/gm_main.py                 # 2 处挂钩（模块加载块 + _b7_live_try_sell 内评估/拦截）
scripts/bootstrap_b7ff_hist.py            # 冷启动回填（CSV + tushare stk_mins 补缺）
scripts/b7ff_daily_review.py              # 每日过滤率 + 被拦腿次日回溯（§6）
t_io/validation/t0_schemes/parity_check_b7ff.py   # parity 对拍硬闸（§1 阶段1）
```

**与实验口径 parity 的纪律**：生产实现不 import t_io/validation 下的 gp_miner/gp_ops
（验证代码不进生产链路），在 `core/b7_factor_filter.py` 内重写最小算子集
（tail30_ret / delay / rolling_min / 时序 z，共 4 个函数、每个 ≤15 行），
并用 `_cache_b7ff_z.json`（实验 z 缓存）做**逐点 parity 对拍**。
**施工实证**：首跑抓到一个真 bug——`h.get("f") or np.nan` 把 f=0.0 误判缺失踢出 z 窗口
（falsy-zero），修复后 421 腿重算：放行集合 82=82、判定不一致 0、z 值超差 0，PASS
（results_b7ff_parity_2026-09-22.json）。硬闸有效，不是摆设。

## 3. 接入点（具体文件:行号）

### 3.1 计算与落盘挂钩（每票每日一次）

**推荐：14:55 惰性计算，不新增 14:30 挂钩。**

理由：§1.3 已证 14:55 用 ≤14:30 切片计算与 14:30 当场计算逐点等价；少一个挂钩点；
天然免疫 gm 推送延迟（14:30 bar 晚到几秒不影响 14:55 决策）。

挂钩位置：**`gm_main.py:2148-2149` 之间**（`_b7_live_try_sell` 内，`day_bars = _b7_day_bars(...)` 
之后、守卫链求值 :2156 之前）插入过滤判定：

```python
# 伪码（施工时定稿）
if _b7ff_active():                       # params 开关 + 模块加载成功
    z = _b7ff_mod.z_at_1430(context, code, gm_sym, now)   # 内部含缓存：当日已算则直接取
    _b7ff_mod.persist_today(code, now, z)                  # F 标量落 b7ff_factor_hist.json
    if z is not None and not (z < PARAMS["b7ff_z_threshold"]):   # F3: z < -1 才放行
        ledger.record_skip(code, date_str, "b7ff_blocked", _tail_pct)  # 见 §7 风险①的拍板项
        _audit_write({"event": "b7ff_block", "code": code, "z": round(z, 4), ...})
        return False                     # 拦截：本票今日 B7 不出手
    # z is None（历史不足/数据缺）→ 默认放行 + 告警留痕（§7 风险②）
```

影子通道 `_b7_shadow_try_signal`（gm_main.py:2056）在 :2084 守卫链求值前插入同式判定
（shadow 模式下永不拦截，只把 z 与「如果拦会怎样」记入台账，见 §6 shadow 设计）。

**备选（不推荐）**：在 on_bar 的 14:30 bar 到达时（gm_main.py:2701 bar 落缓存后）挂钩预计算并缓存。
优点是与实验「14:30 计算」字面一致；缺点是多一个挂钩点、多一份当日状态管理，且对推送延迟敏感。
两方案因果等价，推荐前者。

### 3.2 不触动的部分

- 接回链 `_b7_live_day_open_buyback`（gm_main.py:2334）完全不动——过滤层只拦「卖」，被拦的腿
  根本不开链，不存在「拦了卖还要接回」的问题。
- 守卫链枚举 `SKIP_REASONS`（b7_shadow_glue.py:19-21）是否追加 `"b7ff_blocked"` 属 owner 拍板项
  （该枚举有「追加需拍板」先例，见文件头注释 :15-18）。**草案建议追加**（保持台账归因统一）；
  若 owner 不愿动枚举，则拦截事件只写 `_audit_write` + 台账新事件类型 `b7ff_block`，
  不走 record_skip。

## 6. 监控指标与 shadow 设计

### 6.1 落盘事件（全部复用既有通道）

| 事件 | 通道 | 内容 |
|---|---|---|
| `b7ff_eval` | `_audit_write`（gm_main.py:1356） | 每个 tail30 达标腿的 {code, date, F_1430, z, hist_days, decision ∈ pass/block/na_allow} |
| `b7ff_block` / skip reason `b7ff_blocked` | 台账 b7_shadow_{date}.jsonl + `_audit_write` | 被拦腿留痕（含 tail30_pct、z） |
| `b7ff_filter_{date}.jsonl` 判定日志 | `t_io/logs/`（审批口径②） | **每次 14:55 判定全量一行**：date/code/f1430/z/hist_days/decision/reason/tail30_pct/c1455，无论放行/拦截/na_allow |
| 被拦腿次日回溯 | `scripts/b7ff_daily_review.py`（审批②后替代 shadow 结算：日志已带 c1455，join tushare 次日开盘价按实验口径算虚拟费后净） | 「拦下的腿如果做了会赚多少」的复盘数据源 |

### 6.2 每日复盘脚本 `scripts/b7ff_daily_review.py`

- 当日过滤率 = 被拦腿数 / tail30 达标腿数（实验基线：F3 放行 82/421 ≈ 19.5%，即**过滤率应 ≈ 80%**；
  漂移 >20pp 告警——过滤率不对往往是 z 历史断档或计算 bug，先于收益暴露）；
- 分组费后对比：放行组 vs 被拦组（shadow 虚拟结算）各自 n / 净均 / 胜率，滚动 5 日窗口；
- 与离线实验分布对照：当日 z 分布直方 vs `_cache_b7ff_z.json` 全样本分布（防生产实现漂移）；
- 异常计数：z=NaN 放行次数、hist_days<5 的票数、14:30 bar 缺失票数。

## 11. 模拟盘验证操作手册（owner 操作项）

### 11.1 账户/配置区分现状（勘探结论）

- auto 链**当前只有模拟盘部署**：gm_main.py 以 strategy_id `e8bb1f4d-87ce-11f1-97f7-98fa9b8df5e7`
  跑在掘金新终端**仿真账户**（gm_main.py:3917-3919，`mode=MODE_LIVE`）。
  仓库内**没有独立的实盘配置文件**——`execution/auto/_gm/config/params.py` 是唯一 PARAMS 来源，
  它服务的就是模拟盘终端。
- 因此审批③的落地方式：开关默认 `False` 已入库；**翻 `True` 的动作只允许在模拟盘终端
  运行的这份配置上做**。未来若新建实盘策略（新 strategy_id/新终端），其配置必须保持
  `b7_factor_filter_enabled: False`（params.py:479-489 注释已写明），待模拟盘验证通过后
  由 owner 拍板翻启。

### 11.2 开启验证（owner 三步）

1. **改一个值**：`execution/auto/_gm/config/params.py` 里 `"b7_factor_filter_enabled": False` → `True`；
2. **重启模拟盘策略**：掘金新终端（仿真账户）里停掉再启动 gm_main 策略
   （watcher 会自动拉起，但改配置建议手动重启确保读到新值）；
   启动日志应无 `[B7FF] 过滤层模块加载失败` 字样（有则过滤层自动关闭=纯 B7，查日志）；
3. **确认历史文件在位**：`t_io/state/b7ff_factor_hist.json` 存在且末日 = 最近交易日
   （bootstrap 已回填至 2026-09-21；之后每个交易日 14:55 由策略自动追加当日 F）。

### 11.3 每日看什么

| 看什么 | 在哪 | 正常形态 |
|---|---|---|
| 判定日志 | `t_io/logs/b7ff_filter_{date}.jsonl` | 每票 14:55 一行：code/f1430/z/hist_days/decision/reason/tail30_pct/c1455；decision ∈ pass/block/na_allow |
| 拦截留痕 | 台账 `t_io/logs/b7_shadow_{date}.jsonl` 的 `b7_skip`（reason=b7ff_blocked）+ 审计 `auto_backtrace.jsonl` 的 `b7ff_block` | 被拦腿两处都有，z 值一致 |
| 控制台 | 掘金终端策略日志 | `[HH:MM:SS] B7实单跳过 XXXXXX reason=b7ff_blocked z=... tail30=...` |
| 每日复盘 | `"$DAIMON_USER_PYTHON" scripts/b7ff_daily_review.py --date YYYY-MM-DD`（次日盘后跑） | 过滤率 ≈80%±20pp；被拦腿回溯净均多数 ≤0 |

### 11.4 告警与处置

| 现象 | 含义 | 处置 |
|---|---|---|
| 日志里大量 `na_allow` / hist_days<5 | z 历史断档（bootstrap 缺口或当日未落盘） | 重跑 `scripts/bootstrap_b7ff_hist.py`；连续 3 日同一票 na 属红色项 |
| `guard=align_fail` | 该票当日分钟线不足 211 根/标签错位（停牌、断流） | 默认放行是设计行为；先查数据源，不慌 |
| 过滤率漂移 >20pp | z 计算或历史可能出错 | 当日离线抽查：`parity_check_b7ff.py` 重跑应仍 PASS |
| 被拦腿回溯净均持续为正 | 过滤层拦错（edge 退化） | 翻回 False 回纯 B7，拿数据复盘 |
| 不想验证了 | — | 翻回 `False` 重启策略，即回纯 B7，零残留 |

### 11.5 已知限制（诚实声明）

- **bootstrap 的 9 月历史来自 tushare，上线后的当日 F 来自 gm bar_cache**——两源 F 微差
  （实测 000988 09-21：-0.00044505 vs -0.00045610，~2% 相对差）。z 是 14 日窗口统计，
  单源切换引入的 z 噪声估计 <0.1，方向随机；parity 硬闸是在 gm 源上 100% 过的，
  上线 2-3 周后历史全换成 gm 源，该噪声自然消失。
- z 历史只在「B7 实单通道真正评估该票」的日子落盘（sig 被其他信号占用/KILL_SWITCH
  触发的日子不入账）——hist_days 计数会略少于交易日历，对 z 窗口影响轻微，已知情接受。
- 模拟盘验证期间的费用/滑点与实盘差异不在本层验证范围（B7 本体已在模拟盘跑，
  过滤层只改变「哪些日子出手」）。
