# GUI「卡死」根因与修复（2026-10-10）

> 结论先行：卡死**不是后端慢、不是 JS 卡、不是 GIL 争抢**，而是
> **pywebview 在 UI 线程上执行 `Thread.start()`（会阻塞到新线程被调度）× 环境线程数爆炸**
> 形成的**自我强化死亡螺旋**。
> 主犯是选股标签批算的 `ThreadPoolExecutor(max_workers=40)`。

---

## 1. 症状的一个关键特征：是「卡死」不是「慢」

`t_io/logs/gui_slow_calls.log` 里一次会话只有 **43 条慢调用 / 43 秒 ≈ 1 次/秒**，
但同一时刻进程里躺着 **50~114 个线程**（`t_io/logs/gui_thread_dumps.log` 的 `活线程=` 字段）。

**矛盾的解释**：慢调用日志是前端在 `await` 的 `finally` 里上报的
（`web/app.js::apiCall`）。**挂住永不返回的调用根本跑不到 `finally`，在日志里完全隐形。**
⇒ 日志看起来"只是有点慢"，实际是**调用挂死 + 线程只增不减**。

所以判断这类问题：**不能只看 `gui_slow_calls.log`，必须同时看进程线程数。**

---

## 2. 确证链条（靠 6 份全线程栈）

诊断入口：前端在 `ping` 慢时自动调后端 `dump_threads()`，把**全部 Python 线程栈**落到
`t_io/logs/gui_thread_dumps.log`（解析脚本 `scripts/experiment/gui_freeze_parse_dump_20261010.py`、
`scripts/experiment/gui_freeze_thread_composition_20261010.py`、`scripts/experiment/gui_freeze_find_pandas_20261010.py`）。

### 2.1 UI 泵线程卡在「创建线程」上 —— 这是钥匙

UI 线程（`winforms.py:808 in create` = `app.Run()` 消息循环）当时的栈：

```
threading.py:969 in start            ← Thread.start() 在等新 OS 线程被调度
webview/util.py:336 js_bridge_call   ← 就是 `Thread(target=_call).start()`
webview/platforms/edgechromium.py:251 on_script_notify
webview/platforms/winforms.py:808 create
```

`js_bridge_call` 是**在 UI 线程上**被调用的（WebView2 事件回调跑在 UI 线程），
而 `Thread.start()` 会**阻塞到新线程真正开始运行**（`self._started.wait()`）。
⇒ **每来一个 js_api 调用，UI 线程就被"创建线程"卡住一次。**

### 2.2 环境线程数爆炸，主犯是标签批算的 40 并发池

6 份 dump 的线程归类（`scripts/experiment/gui_freeze_thread_composition_20261010.py`）：

| dump | 活线程 | pandas/numpy | 堵在返回路径 | 网络 |
|---|---|---|---|---|
| #1 | 109 | 34 | 15 | 17 |
| #2 | 68 | 30 | 19 | 3 |
| #3 | 50 | 0 | 39 | 0 |
| #4 | 114 | 38 | 45 | 3 |
| #5 | 69 | 25 | 14 | 7 |
| #6 | 72 | 35 | 20 | 5 |

**最大的一类一直是 pandas/numpy（25~38 个）**，且 **160/162 个来自 `futures._worker`**
（= 线程池 worker），业务帧高度集中（`scripts/experiment/gui_freeze_find_pandas_20261010.py`）：

```
121  t_gui.py:_stock_tags_from_df
120  t_gui.py:_stock_tags_one
119  adapter.py:get_trend30
119  t_gui.py:_trend30_trend
101  adapter.py:evaluate_bars
 42  indicators.py:add_30min_indicators
```

⇒ 全部来自 `load_stock_tags_batch` 的 **`ThreadPoolExecutor(max_workers=40)`**。

### 2.3 死亡螺旋

```
js_api 调用 → UI 线程 Thread.start()（阻塞等调度）
     ↑                              ↓
线程更多 ← semaphore.acquire 永不醒 ← UI 线程跑不了 ExecuteScriptAsync 回调
                                        ↑
                              环境线程多 ⇒ Thread.start() 更慢
```

实测 **25 个线程堵在 pywebview 返回路径**：21 个在
`edgechromium.py:160 semaphore.acquire()`（**无超时**）、4 个在 `:152 self.webview.Invoke(...)`。

### 2.4 旁证（三条独立佐证）

| 观测 | 值 | 说明 |
|---|---|---|
| GUI 进程 CPU | **14%**（WebView2 进程 6%） | **不是在算，是在干等** ⇒ 排除 GIL/CPU |
| 空端点 `ping()` 往返 | 中位 **6.7s**，max 29.7s | 后端本征 ~0 ⇒ 全是投递开销 |
| JS 主线程阻塞 | 中位 753ms，max 810ms | **堵不住 6.7 秒** ⇒ 排除"JS 渲染卡住" |
| 前端到达率 | ~1 次/秒 | **不是洪泛** ⇒ 是线程不退出 |

## 3. 修复

### 3.1 后端：标签批算并发度 40 → 6（`t_gui.py::load_stock_tags_batch`）

**为什么几乎不损吞吐**：这些线程大部分时间在等 `facade` 那个**单 worker 的 GM 池**
（栈里可见 `facade.py:_gm_call` / `futures.result`）。40 并发换不到并行度，只换来 40 倍线程压力。

**实测**（`scripts/experiment/gui_freeze_probe_tags_threads_20261010.py`，40 个标的）：峰值线程增量 **+40 → +13**
（其中 executor worker 从最多 40 降到 6）。

**代价**：标签批算整体变慢，首次进建仓表/破位表时标签"稍后才自填"。前端本就轮询补齐，可接受。

### 3.2 前端：`apiCall` 加超时 + 在飞上限（`web/app.js`）

- **超时 20s**：挂住的调用必须能放弃等待。否则配"非重叠轮询"会让该轮询器**永久停摆**
  （前一轮改动引入的风险）。
- **全局在飞上限 6**：到达率不必超过服务率，靠堆积就能把队列撑爆；限流把队列钉成有界。
- 正常情况（调用 <1s）6 个名额绰绰有余（约 1 次/秒的需求），只有冻结时才会被限到。

### 3.3 埋点降载（它自己原来也是负载源）

- `report_slow_call` / `_diagReport` **节流 2s**。原先"每次慢调用都再触发一次上报"，
  冻结时**把队列翻倍**。
- `dump_threads` **取消自动触发**（一次写 100KB+ 栈，且它本身是个 js_api 调用）。
- `ping` 探针 2s → 10s，并改走 `apiCall`（受在飞上限约束，不再绕过限流）。

## 4. 教训（比结论更值钱）

**我上一轮用「把池钳到 8，`load_console` 延迟没变差」否掉了这个池——那是错的。**

那次是**孤立测的**：只看了单个接口延迟，没意识到真正的瓶颈是
**环境线程数拖慢 UI 线程的 `Thread.start()`**，而不是 GIL 争抢。

⇒ **测"某个池要不要收"，必须看它对全局线程数的影响，不能只看单个接口的延迟。**

同理，前两轮把结论归到"投递层排队"和"前端轮询叠加"——方向不算错（都在这条链上），
但都没指到**可修的那个点**。**能修的点是"减少环境线程数"，不是"改 pywebview 内部"。**

## 6. 尚未验证

以上修复**都是离线验证的**（探针 + 线程数），**没有实跑 GUI 确认**。
重启 `t_gui.py` 后应检查：

1. `gui_thread_dumps.log` 里 `活线程=` 是否显著低于 100（目标 < 40）；
2. `gui_client_diag.log` 里 `ping` 中位往返是否从 6.7s 降下来；
3. 是否还出现 `api_timeout` 记录（有 = 仍在挂死）。

若仍有挂死，下一步方向（按可能性排序）：
- 继续压其它线程源：`_fetch_daily_bounded`（每调用新建一个单 worker 池并 `shutdown(wait=False)` 弃池，
  与之前修掉的 `_em_last_price_bounded` 是同一模式）、`prewarm_*` 启动 8 个重活线程；
- 把前端 10s 轮询组**合并成一个 bundle 端点**（~10 个调用 → 1 个），从源头减少
  `Thread.start()` 次数。注意：**这才是治本的方向**——UI 线程每创建一次线程就被卡一次。
