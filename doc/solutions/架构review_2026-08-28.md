## 二、核心问题（按对可持续迭代的杀伤力排序）

### 🔴 P0 — 做T引擎仍是两个分叉

合并方案 §5.2 里明确列为"硬卡点"的部分，目前完全没动：

- `_gm/signals/engine.py:77` 的 `ScoringEngine`（~14 个 score_* sigmoid 因子）vs `core/signal_engine.py:91` 的 `SignalEngine`（swing2pt + renko）。
- 两分支已分叉 5 周，各自打过实战补丁（goldminer WP-B07/B14/B15/B18…，superTrader 否决因子/门控）。**同名不同行为**是最危险的 bug 温床——未来任何一处改因子，都要记得改两处。

这是唯一一个"要不要继续做"需要用户拍板的问题（见 §四）。

### 🔴 P1 — 两个 god-file 用了反模式

- `main.py`（3099 行）：`exec 共享命名空间` 是方案里点名的"引擎抽取最大卡点"。所有模块在同一个 namespace 里 exec，靠**可变全局对象的引用同一性**工作（VIRTUAL_TRADES/HOLDINGS）。任何函数都隐式依赖一堆不知道从哪来的全局，无法单测、无法复用、无法安全重构。
- `t_gui.py`（4098 行）：~70 个 Api 方法塞在一个文件，其中 4 处还直连网络（方案 §5.4 说好的改走 provider 未完成）。

### 🟠 P2 — 一整层死掉的 Phase3/4 脚手架

这些文件**只有自己的测试在 import**，运行时零参与：

- `core/trading_system_coordinator.py`、`core/config_manager.py`、`core/config_validator.py`、`core/dto.py`、`core/metrics_tracker.py`、`core/optimization_pipeline.py` —— 只有 `tests/phase3/` 在引用。
- 整个 `src/`（Phase4 标准化结构）**95% 是死的**：只有 `src/holdings_sync.py`（main.py:1646 在用）和 `src/data_fetcher.py`（被一个指向不存在 `src.main:main` 的 `scripts/setup.py:57` 引用）活着。
- `optimization/` 零引用；`stock_hunter/` 只剩一个测试引用。

**后果**：改代码前得先花大量精力判断"这个文件到底活不活"，直接违背"可持续迭代"。

### 🟠 P3 — 配置有 5 套系统

| 配置源 | 作用 | 状态 |
|---|---|---|
| `config.py`（1009 行） | 手动侧 PARAMS 真源 | 活 |
| `config/auto_pool.py` | 自动池真源 | 活 |
| `_gm/config/params.py`（438 行） | goldminer 参数 | 活（独立副本） |
| `core/config_manager.py` + `config/` yaml | Phase3 配置中心 | 死 |
| `src/config/schema.py` + `utils/config/manager.py` | Phase4 pydantic | 死 |

`core/build_decision.py` 里还有 `DEFAULT_TIMING_PARAMS` 内嵌兜底副本（因 goldminer 无法 import 顶层 config.py），靠单测 `test_default_params_match_config` 手动对齐，脆弱。

### 🟡 P4 — 潜在地雷（不报错，一碰就炸）

- `main.py:673` / `main.py:2317` 还在 `from fake_signal_monitor import ...`，但 `fake_signal_monitor.py` 已被删除（清理时删的）。懒加载 import，跑到对应代码路径才炸。
- `scripts/setup.py:57` 入口指向 `src.main:main`，该文件不存在。

### 🟡 P5 — 测试布局失衡

- `t_io/validation/` 下 96 个校验脚本（`test_wp_b07.py`、`test_fix_20260728.py`…），本质是"一次性验证脚本"被当成测试库永久堆积。
- `tests/` 下只有 6 个，且其中 `tests/phase3/` 测的是已经死掉的脚手架。

## 三、优化建议（分三期，按风险从低到高）

### 期 A：止血（低风险、纯清理，可立即做）

1. **删死代码**：`src/`（保留 `holdings_sync.py` + `data_fetcher.py` 两个活模块挪到 `core/` 下）、`core/trading_system_coordinator.py` + `config_manager` + `config_validator` + `dto` + `metrics_tracker` + `optimization_pipeline` + `tests/phase3/`、整个 `optimization/`、`stock_hunter/`。
2. **修地雷**：删掉 main.py 里两处 `fake_signal_monitor` import；修正 `scripts/setup.py` 的入口。
3. **配置收敛**：合并 3 套活配置（`config.py` + `_gm/config/params.py` + `core/build_decision.py` 的 `DEFAULT_TIMING_PARAMS`）为一个 `config/` 下的单一加载入口；死配置随期 A-1 一起删。

### 期 B：结构（中等）

4. **完成 `execution/manual/` 拆分**：把 `main.py` 执行逻辑、`execution/auction_analyzer.py`、`daily_sentiment.py`、`preopen.py` 收进 `execution/manual/`，兑现方案 P4 目标结构。顺手把 `main.py` 的 exec 共享命名空间改成显式注入（`core/signal_engine.py` 已做 `EngineContext`，路径走得通）。
5. **拆 god-file**：`t_gui.py` 按 Api 域拆模块；`analysis/index_regime.py`（2725 行）、`core/position_builder.py`（2014 行）先拆出纯函数部分。
6. **收敛测试**：`t_io/validation/` 已"毕业"的脚本归档或转正式 `tests/` 单测，保留唯一回归入口。

### 期 C：制度（长期）

7. **P2 引擎同源**——唯一需用户决策的大项（见 §四）。做则按方案 §5.2 逐补丁裁决；不做则显式冻结边界、写死约束文档，避免"半同源"灰色地带。
8. **更新架构文档**：`CURRENT_STATUS.md` 已严重失真（引用已删除的 `optuna_parameter_optimization.py`、根目录 `position_builder.py`）。每期清理后同步更新，让文档重新成为可信地图。

## 四、需用户拍板的决策点

整个 review 里只有一个问题真正需要决定，其余都是"做了显然更好"：

**做T引擎（signal_engine）要不要继续合并成单一真源？**

- **继续合并**（方案 P2 原计划，3-4 天）：消除"同名不同行为"最大隐患，但风险高——5 周分叉补丁要逐条对账，破闸即回退。
- **显式不合并**（保持两引擎独立，0 天）：省掉最大不确定项，但必须写死边界文档 + 用 `build_verdict_parity.py` 之类的双跑对照持续兜底。

建议：先做期 A + 期 B（清理 + 结构），把地图弄干净之后再决定 P2。因为混乱状态下，任何引擎对齐工作都会在"这个文件到底用不用"上白白浪费精力。
