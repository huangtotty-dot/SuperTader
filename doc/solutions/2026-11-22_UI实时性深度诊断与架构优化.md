# UI 系统实时性深度诊断与架构优化（2026-11-22）

> 依据：三路并行只读审计（gui.py 后端 16,836 行 / web 前端 15,272 行 / t_io 数据供给链），全部结论带 file:line 实锤。
> 对照基线：`2026-10-26_系统优化_实时性与负载.md`（那轮 P0/P1 经逐条验证：**全部修复且未复发**）。

## 一、总体判断

**10-26 治好的是"读文件"，11 月新代码病在"算和网"——新功能上线时绕过了自己定下的工程纪律。**

架构方向依然是对的（bundle 合帧、SWR、指纹缓存、QuoteBus、错峰非重叠轮询都已体系化）。当前体感"不够实时"的来源收敛为三条新病根：

| 病根 | 最扎眼的证据 | 用户体感 |
|---|---|---|
| **① 相位病复发**：新端点 TTL ≈ 轮询周期，每拍穿透缓存 | 盘面实时价**结构性滞后 10~25 秒**（quotes fresh=8s vs 轮询 10s，每拍都吃上一拍的剩饭）；`load_mw_head_stats` TTL 8s < 轮询 10s，一个小卡片每拍双网络、avg 4.1s | 价格总是慢一拍 |
| **② 重活压桥**：秒级同步计算/同步网络放在 js_api 调用线程 | 异常池整表重算 **avg 6.6s / max 84s**（15s 轮询）；风向标组包全时段 13,785 次慢调用 avg 1.8s；连空 `ping` 都被排队拖到 avg 5.7s | 点了没反应、卡片转圈 |
| **③ 全量快照过桥**：桥单次往返 0.4~3.8s，payload 只涨不跌 | 成交流水每 10s 全量 0.5~1.5MB（界面只看尾 200 条）；PB 大表每拍 ~100-300KB + 2,000~6,000 个 DOM 节点全量重建 | 越用越钝、切页掉帧 |

外加一条隐藏最深的：**持仓变化 → GUI 持仓页是全系统最慢的链，最坏 ~6.2 分钟**——10-26 把心跳 SDK 降频到 300s 后，成交事件没有反向打通缓存失效，出现"看到成交、持仓不变"的割裂。一行失效逻辑即可修，**性价比全表第一**。

供给层最大冗余：QuoteBus 只收编了"老五路"，10-21 后新增的九宫格（9 格 × 4.6s ≈ 2 rps 直连腾讯）与 ma5_pullback（每 30min 1669 只直连）在总线外重建了三套直连，腾讯侧稳态请求量反而比收编前更高（~4 rps vs <0.5 rps）。

## 五、架构治理：三条铁律工程化（防同型复发）

11 月的病全是"新代码绕过老纪律"。把纪律从注释变成闸门：

1. **TTL ≠ 轮询周期**：新端点注册时必须声明服务周期，与前端轮询周期做 lint 校验（相等或略小即报警）。同型已复发 3 次（P1-9 → mw_head_stats → sentiment_live）。
2. **js_api 调用线程禁止同步网络与秒级重算**：统一走「旧值立返 + 后台单飞刷新」SWR 模板；新端点 code review  checklist 第一条。
3. **行情消费必走 QuoteBus**：新增 `TencentProvider` 直接实例化的代码即 lint 报警（九宫格、ma5_pullback 两个漏网就是这么来的）；同时补齐 bus 欠的令牌桶/熔断（10-26 挂账）。

配套：把这三条写进 `AGENTS.md`/贡献约定，并在 tests/phase3 加 guard 测试（仿 `test_http_pool_shared.py` 的先例）。
