## 0. ⚠️ 前提发现：B7 的生产通道**从未运行过**

这不是推测，是三条独立证据：

**证据一（静态，判定性）**：三个开关**都不在 `PARAMS` 里**，而闸函数读的是 `PARAMS`：

| `b7_live_enabled` | **False** | True | **True** |
| `b7_factor_filter_enabled` | **False** | True | False |

`gm_main.py:26` 只 `from config.params import PARAMS, STOCK_PARAMS`（**不 import `INDEX_REGIME_PARAMS`**），
而 `_b7_shadow_enabled:1838` / `_b7_live_enabled:1849` / `_b7ff_enabled:1881` 全部 `PARAMS.get(...)`
⇒ **三者恒为 False**。

**证据二（历史）**：错放**自引入起就存在**，不是后来被改坏 ——
`git show 8f507d07:execution/auto/_gm/config/params.py`（即「B7实单施工」那个 commit）
显示 `b7_shadow_enabled` 在 L465、`b7_live_enabled` 在 L474，**均在 `INDEX_REGIME_PARAMS` 内**，
而该 commit 的 gm_main 同样只 import `PARAMS, STOCK_PARAMS`。

**证据三（实证）**：`t_io/logs/`、`t_io/state/`、`gmcache/` 中
`b7_live_sell` / `b7_live_buyback` / `b7_signal` / `b7_skip` / `b7_eval`
**命中文件数全部为 0** —— 一条事件都没产生过。

### 推论

1. **删除 B7 在生产侧是「行为中性」的** —— 删掉的是一段从未执行的死代码 + 只服务回测的路径。
   这让删除比预想的安全得多。
2. **owner 记忆中的「B7 实单已开 / 首窗 5/5 全亏」不可能来自生产**，只可能来自
   **回测/回放路径**（`SUPERTRADER_B7_BACKTEST` / `--b7`）。⚠️ 相关历史结论的归因需重新核对。
3. **顺带拆掉一颗地雷**：一旦有人「好心」把这三个键从 `INDEX_REGIME_PARAMS` 搬到 `PARAMS`，
   `b7_live_enabled=True` 会**立刻让实单通道真正启用**。删除即消除该隐患。
