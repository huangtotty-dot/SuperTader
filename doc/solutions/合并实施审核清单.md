## 审核原则

1. **设计文档是唯一基准**：实施偏离方案 §5/§6 契约的，要么改实施、要么回改文档（需用户确认），不允许静默漂移。
2. **每阶段有验收闸**：证据驱动（测试输出/对照数据/日志），不接受"应该没问题"。
3. **不破生产**：合并期间 superTrader 人工链路（做T推送/建仓扫描/复盘）任何回归都视为破闸。
4. **代码级红线**（任一触碰即打回）：
   - 掘金 token 或飞书 webhook 明文进入版本库；
   - bridge jsonl 出现双写者（单文件单写者纪律）；
   - 修改 goldminer 现有事件 schema 字段（只允许扩展命名空间）；
   - 破坏 `t_qty 只减不增` 不变量（src/holdings_sync.py）；
   - 引擎 API 退化为隐式读取系统时钟（必须保持时间注入，保回测可重现）。

### P0 打回记录（2026-08-28）

**通过的部分**：token 已移出两仓库 git（goldminer 2c217a0 + superTrader 016c26b6）；.gitignore 覆盖正确；`utils/gm_token.py` 读取顺序合理；probe 脚本结构与报告格式规范。

**致命问题（打回原因）：实测报告当前不可复现——`t_io/state/gm_config.json` 中的 token 无效。**

审核方实测证据链：
1. 用 gm_config.json 当前 token 调 `history_n` → gm 服务器返回 `{"status":1000,"message":"错误或无效的token"}`（重试含 strip 均失败）；
2. 该 token（36 字符）与 goldminer git 历史中的旧 token（40 字符）不同——旧 token 同样已失效；
3. **根因**：国盛定制版 gm SDK 的数据接口认证的是**掘金终端会话 token**（`gmterm-serv.exe` 启动参数 `--token=`，随终端重启轮换）。审核方用当前运行中终端的会话 token 实测 `history_n` **成功**（600481 日线返回正常）；
4. 时间线推测：10:19 的 probe 报告可能用的是当时有效的终端会话 token，10:25 写入 gm_config.json 的静态 token 本身就不是有效凭证。

**打回项（实施方修复要求）**：
1. **token 机制重做**：静态 gm_config.json 不成立。改动态发现——WMI/`psutil` 查 `gmterm-serv.exe` 进程命令行解析 `--token`（审核方已验证可行）；终端未运行 → 返回 None → facade 降级腾讯并 log 告警。gm_config.json 保留为兜底/覆盖。实施方案 P0-2 已同步修正；
2. 修复后用有效 token **重跑全量 probe**，报告须加**每只标的行数校验**（现仅 first_rows 验证首只），daily 要求 min(rows)==800、minute min(rows)==240；
3. **subscribe 证据补强**：裸 `subscribe()` 无 run() 上下文不能证明能收到 bar——改为在终端策略上下文或 run() 回调内验证 41 只实际收到 60s bar（goldminer 生产仅覆盖 17 只，41 只是新证据域）。

**给用户的提示**：掘金终端必须保持运行且登录，gm 数据链路才可用——这是合并后系统的运行时依赖，请知悉。
