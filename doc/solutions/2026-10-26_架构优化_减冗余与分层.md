# 架构优化：减冗余与分层治理（2026-10-26）

> 来源：全仓架构审计（915 个 .py，基于 HEAD=e961feb，P2 已落地）。
> 目标：减少冗余、层次归位，不碰交易执行正确性。

## 一、审计核心发现（摘要）

### 系统真实拓扑（3+1 进程）
| 进程 | 入口 | 职责 |
|---|---|---|
| 盯盘引擎 | `main.py` | 信号扫描 + 9 个定时钩子 + 飞书告警（**不下单**） |
| 交易执行 | `execution/auto/gm_main.py` | OSC 策略执行体（唯一 import gm.api） |
| GUI | `t_gui.py`（13,171 行）+ `web/app.js`（9,568 行） | pywebview 壳 + 前端 |
| 猎手管线 | `stock_hunter/main.py` | 概念打分离线管线（GUI 按需拉起） |

### 冗余大头（按严重度）
1. **main.py 的 exec 共享命名空间加载器**（main.py:34-102 + 226）：11 个模块被 exec 进共享 dict 再灌进全局，同时又对其中 4 个模块做真实 import ——同名类/函数存在**两份身份**，`add_5min_indicators` 等新旧两版同名函数靠 exec 顺序静默遮蔽，**改 import 顺序就会改信号口径**。全仓最高风险点。
2. **`execution/auto/_gm/` 整体 vendored fork**（18 文件 447K）：config/analysis/signals/utils 五件套各有一份缩小版副本，与正本各自演化 → 交易侧与监控侧阈值可静默漂移（例：osc_sell_time `_gm/config/params.py:264` vs `config.py:962`）。
3. **t_gui.py 巨型文件**：`class Api` 一个类 1 万行 ~200 个方法，箱体/通道/支撑压力/斐波那契（~470 行）、两个完整扫描器（~770 行）、PnL/风控核算（~500 行）等**纯算法长在 GUI 里**，且箱体算法与 core/position_builder.py 是双份。
4. **小工具散落**：JSON 读写封装 7+ 套（原子写口径不一致）；代码归一化 5 处；涨停四档阈值 9.5/19.5/29.5/4.5 在 stock_hunter 一个文件内重复 4 次 + sector_rotation 第 5 处；"t_io" 字面量 552 处/144 文件。
5. **死代码**：3 个零调用整文件（~1,600 行）+ main.py 空壳路由/死分支 + stock_hunter 根目录 ~75 个一次性迁移脚本 + 45 个 watchlist .bak。
6. **飞书客户端 4 套**（config.py / push_feishu.py / daily_sentiment.py / gm_bridge/feishu.py，webhook 来源 3 种）。
