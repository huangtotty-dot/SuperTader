## P0-1 回补 armed 硬帽（Q-20260911-1）—— 估时 0.5h

**事故**：09-11 588170 回补 armed 1,100 → 实下 21,000（19.1×）；600481 armed 900 → 2,600。根因：回补路径仅绕过确认闸，下单量由 sizer 按「mirror 底仓+30%T」决定，无 armed 量约束。

**⚠️ 字段名勘误**：`_ab_now` 字典真实 key 是 **`sell_qty`**（`t_engine_auto.py:494-517 arm_awaiting_buyback` 返回结构；跨日恢复 `sell_state.py:208/:226` 同 key）——用 `_ab_now.get("qty")` 会恒为 None、帽子失效。

**改动点**（`execution/auto/gm_main.py`，:2015 与 :2017 注释行之间插入，即 sizer 出量之后、降档之前）：

```python
        # Q-20260911-1: 回补帽——回补量封顶为 armed 卖出量（sell_qty），
        # 防 sizer 按预算/底仓口径出量失控（09-11 588170 armed 1100 实买 21000 ≈19×）
        if _ab_now:
            _bb_cap = int(_ab_now.get("sell_qty") or 0)
            if _bb_cap >= 100 and qty > _bb_cap:
                _audit_write({"event": "buyback_capped", "code": code,
                              "qty_before": qty, "qty_after": _bb_cap,
                              "sell_qty": _bb_cap, "time": str(now)})
                qty = _bb_cap
```

设计要点：帽在降档前（降档只会再减半，无副作用）；在现金预检（:2036）前，两道 min 不冲突；`_bb_cap < 100` 不动 qty 交给既有最小单元闸；留痕 `buyback_capped` 供复盘统计。

**验证**：回放 09-11 13:49 bar（588170 armed sell_qty=1100）→ 下单量 21,000→1,100 且审计流出 `buyback_capped`；非回补路径（`_ab_now=None`）行为逐字节不变（replay_verify 全量比对）。

**风险**：极低。注意：未来若引入部分成交（status==2）arm 需重审帽口径（当前 sell_qty=该笔全成量，与待回补总量语义一致）。

## P0-2 成交回报链路冻结根治（Q-20260911-2，含 Q-20260911-3 审计误报）—— 估时 4~6h

**事故现场**：14:50 TAIL 下单成功（sell_channels.py:352 print 已出、execrpts 证实 14:50:02 成交）→ on_bar(14:50) 未返回 → 心跳停 14:50、fill 缺席、进程活死人（PID 35692）。**单一根因**：on_bar 阻塞连坐 SDK 事件派发线程，`on_order_status`（fill 唯一入口，gm_main.py:2160→:2198 write_fill）永久排队。心跳在 bar 循环前写（gm_main.py:1395<1403），故 14:50 心跳有、14:51 无 = on_bar 未返回的实证。精确挂死行号无法从现有证据钉死（区间=sell_channels.py:352 之后~on_bar 返回之前；首要嫌疑=第二只超仓票的 TAIL 下单进半死 SDK 会话）。

### Fix A — 全部直调 SDK 点位套硬超时（与 facade._gm_call 同款）

裸奔点位全量（8 处 11 点）：`sell_channels.py:323`（TAIL order_volume）、`sell_channels.py:147`（仲裁器）、`gm_main.py:2066`（买入）、`gm_main.py:1643`（BASE 建仓）、`gm_main.py:611/1027/1175`（history_n）、`gm_main.py:965`（current）、`gm_main.py:532/891`（positions）、`gm_main.py:1109/1385/1965`（cash）。

改法：新增模块级 `_sdk_call`（单 worker ThreadPoolExecutor，`result(timeout=15)`，超时弃池重建抛 TimeoutError，由调用点既有 except 接住走拒单/告警路径），逐点替换。下单链路超时 15s（略宽于数据侧 12s）。

```python
# sell_channels.py:323 示例
# before: order_volume(symbol=gm_sym, volume=qty, side=OrderSide_Sell, ...)
# after:
_sdk_call("order_volume_tail", order_volume,
          symbol=gm_sym, volume=qty, side=OrderSide_Sell, ...)
```

**验证**：mock order_volume sleep 300 → 15s 抛 TimeoutError → 走既有「下单失败」print + `write_risk("order_failed")`；次日心跳/事件流连续。
**风险**：① gm SDK 非回调线程下单的线程安全性无官方背书——facade 数据侧已有生产先例，**下单侧先在仿真盘跑一天**；② 超时弃池的挂死线程占内存（低概率可接受）；③ **超时≠未成**（单可能已报柜台）——必须配合 Fix B 对账，否则台账与柜台分叉。

### Fix B — fill 记账与下单解耦（大手术，唯一重改）

1. 四处下单点成功后登记 `context._pending_recon[symbol] = {code, side, qty, px, ts, order_ids, closed: False}`（order_volume 返回值当前被丢弃，:1643/:2066 的 _oid 利用起来）。
2. `on_order_status` 的 status==3 分支（gm_main.py:2178-2309 约 130 行）**纯机械抽取**为 `_apply_fill(context, symbol, side, volume, price, order=None)`，回调与轮询共用。
3. 防重闸 `context._fills_done`：key=`(symbol, order_id, volume)`；TAIL 无 order_id 退化 key=`(symbol, side, volume, minute_bucket)`。回调/轮询入口先查后插。

**验证**：回放 09-11 包，人为丢弃 on_order_status → 轮询补出等价 fill 且 `_fills_done` 阻断回调迟到二次入账；抽取前后 replay_verify 审计流逐字节一致。
**风险**：130 行抽取是本次唯一大手术——**不改语义，抽完全量回放比对再上线**。

### Fix C — 回调失效轮询兜底（挂 on_bar 头部心跳前，gm_main.py:1365 附近）

每根 bar（60s 自然节拍）扫 `_pending_recon`：age<90s 信任回调不轮询；≥90s 用 `_sdk_call("get_orders", get_orders)` 查当日委托，status==3 → `_apply_fill` 补记 + `write_risk("fill_recovered_by_poll")` + closed=True。整段 try/except fail-open 不阻塞 on_bar。

**验证**：仿真下一单后 monkeypatch 吞掉回调，90s 后 events 应出 fill + risk 留痕。
**风险**：get_orders 也是 SDK 同步调用，**必须走 Fix A 超时**，否则兜底变第二个挂死点。

### Fix D（可选，独立登记）— watcher 活死人终结者

watcher.py:230 心跳过期只告警不处置。建议：交易时段内心跳过期 >5min 且连续 3 次 → taskkill 策略 PID + 飞书确认性告警，依赖终端自启/人工重启。防误杀三闸（交易时段+连续过期+告警先行）。**不阻塞 A/B/C，单独 Q 单排期**。
