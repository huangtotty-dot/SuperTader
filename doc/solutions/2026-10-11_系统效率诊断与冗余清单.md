## 一、先纠正前提：进程拓扑

```
python main.py  ──► [进程A] 盯盘：while True + scan_once() + sleep(15)，池=7 只，不下单
      └─► subprocess.Popen ──► [进程B] GUI (t_gui.py)，只读 JSON、独立进程

python gm_main.py ──► [进程C] 唯一下单者：掘金 subscribe(60s) 事件驱动，40 个 symbol
                       （由 scripts/auto_process_guardian.py 或掘金终端拉起）
```

**证据**

| 论断 | 证据 |
|---|---|
| main.py 不下单 | [`_route_auto_signal`](main.py#L293-L296) 是空 `return` 占位；main.py 全文件**无** `import gm.api`、无执行层下单调用 |
| main.py 只盯 7 只 | `load_holdings()` → `holdings_manual.json` 中 `qty>0` = 实测 7 只（588170/600362/600584/002176/688008/300054/300456） |
| gm_main 是唯一执行者 | 全仓唯一 `import gm.api` 入口；[GM `subscribe`](execution/auto/gm_main.py#L2385) `frequency="60s"`、[`on_bar`](execution/auto/gm_main.py#L2854) |
| GUI 是独立进程 | [main.py:2991](main.py#L2991) `subprocess.Popen([sys.executable, gui_path])` |

> **要点**：GUI 的生死与交易链路解耦。GUI 卡死 = 你看不见系统，**不等于**交易在丢单。

## 二、问题 ① 判定：能否支撑？分三块

### 2.1 交易链路（gm_main）：能，且"卡壳致损"的主要路径已被设计挡住

**最该担心的场景**：guardian 在 09:31 后重启 gm_main —— `_S1_EXEC_DONE_DATE` 是模块级变量，重启即清零，S1 会不会**重复下单**？

**结论：不会。** 两套计划都从**实时账户状态**派生，而非从计划文件回放：

| 计划 | 关键行 | 为什么重启安全 |
|---|---|---|
| 买 | [`build_buy_plan`](execution/auto/s1_executor.py#L226-L231) | `need_val = max(0, tw*equity − held_val)`；第二遍看到已持仓 25% ⇒ `qty_target=0` ⇒ 顺延"已达目标权重" |
| 卖 | [`build_sell_plan`](execution/auto/s1_executor.py#L184-L190) | 清仓循环跳过 `buys ∪ holds`；已被卖掉的旧持仓 `qty=0` ⇒ 自然无操作 |

**内存**：[`bar_cache` 有 480 根上限](execution/auto/gm_main.py#L3298-L3299) → 40 symbol × 480 根，无泄漏。gm_main 模块级无任何无界容器。

**周一就绪度（我实跑验证）**：`python scripts/s1_executor_dryrun.py` → **5/5 场景通过**（清仓/现金截断/部分成交/拒卖/T+1）。产物隔离在 `t_io/state/s1_book/dryrun/`，未污染生产账本。

> 一个仍未验证的耦合：弱转强盘前预筛（[gm_main.py:3022-3028](execution/auto/gm_main.py#L3022-L3028)）跑在 `on_bar` 里，09:31 会阻塞**当次**回调。GM 退化时按 8 次批量调用算约 32s。因 S1 排在它**之前**（[3007](execution/auto/gm_main.py#L3007) vs [3022](execution/auto/gm_main.py#L3022)），且 OGR 窗口有 4 分钟缓冲（[09:31–09:35](execution/auto/gm_main.py#L2446)），目前不外溢。但**弱转强一旦翻启要盯这条**。

### 2.3 GUI：唯一有实锤问题的部件 —— 且修复**未消除**卡死

⚠️ **本节更正我 2026-10-11 早先的口头结论。** 我先看到 `gui_freeze.log` 停在 21:04、修复提交于 21:18，据此说了"修复后无新记录"。**那是错的** —— 该文件在我检查之后仍在增长（2.72MB → 3.15MB，mtime 21:04 → 23:25）。实测复核如下。

**时间线（关键）**

```
10-09（交易日）  161 条记录 / 59 个独立冻结段；交易时段内 57 条 / 45 段，持续 12–44s   ← 修复前
10-10 21:17–21:20 旧会话末段冻结，随后结束
10-10 21:18:46   修复提交 869063c
10-10 22:59:10   新会话启动（= 修复后的代码，见下证）
10-10 23:00:04 → 23:25:06   又一段冻结，持续约 1514s（25 分钟），50 条记录   ← 修复后
```

**"跑的是修复后代码"的证据**：`869063c` 是**最后一个**改动 `t_gui.py` 的提交；工作区与 HEAD 一致（`git status` 干净）；修复标志 [`max_workers=6`](t_gui.py#L4688) 在文件中。

**但修复确实起了一半作用** —— 对比 23:25:06 现场与修复前：

| 指标 | 修复前 | 修复后（23:25 现场） |
|---|---|---|
| 线程数 | 50–114 | **8** |
| pandas 线程 | 25–38 | **0** |
| 卡在哪 | `_stock_tags_*` / `get_trend30` 帧 | `webview/platforms/winforms.py:808` |

**新签名解读**：`winforms.py:808` 是 pywebview 的 **`app.Run()`**（WinForms 消息泵），且 50 个现场**签名完全稳定**。消息泵里等待消息**本身不是死锁**。真正停摆的是前端 —— `gui_client_diag.log` 同期记录 **JS 主线程被阻塞 49–59s**（`jsblock 59748ms`），空端点 `ping` 往返 **4.5–11.4s**。

**触发源指向"慢调用堆积"**（`gui_slow_calls.log`，23:00–23:05）：

```
load_auto_pnl        17173ms / 12231ms / 5159ms
load_stock_tags_batch 12147ms / 3049ms / 2143ms
load_auto_status      9379ms
load_stock_chart      7079ms / 3621ms
ping                  6131ms
```

前端高频轮询多个端点，每个 1–17s，桥接层串行 ⇒ JS 主线程被拖住 ⇒ 心跳停 ⇒ 看门狗判"卡死"。

> **⚠️ 重要限定（不可外推）**：这段发生在**周六夜**，而本机 GM 在非交易时段常不可达 —— 每次 GM-first 调用要先付约 4s 再降级腾讯，**把所有耗时整体抬高了**。因此 23:00 这次冻结**不能直接推断交易日会重现**。
>
> 反过来，**修复前的 10-09 那 57 次交易时段卡顿（12–44s）才是真实交易日的证据**，而它属于修复前。

**对周一的意义**：修复把线程爆炸这条根因消灭了（114→8，有据），但**残留机制未解**，且交易日表现**尚无任何数据**。周一（10-12）是修复后的**第一次交易时段实战**。

## 五之二、CPU 优化（owner 2026-10-11 定为「重点中的重点」）

### 机器约束（一切并发度的前提）

**4 物理核 / 8 逻辑核**，内存 15.7GB（可用 **4.1GB**）。⇒ 任何 >4 的线程池都是超额订阅；
此前 GUI 的 `max_workers=40` 在这种机器上必然是灾难。

### 测量工具（"系统 / 每日"的地基）

| 工具 | 作用 |
|---|---|
| `scripts/experiment/cpu_sampler.py` | **进程 + 每线程** CPU 归因（Windows 下 psutil 每线程 user/system time 可用，**不需要 py-spy**）。`--report` 出按天×按角色汇总 |
| `scripts/experiment/cpu_bench_hotpaths.py` | **可复跑热点基准**（真实缓存数据）。`--report` 出跨日趋势；`--baseline` 标基线 |

### 首轮成果（背靠背 A/B，n=25）

| 函数 | 改前 | 改后 | 变化 |
|---|---|---|---|
| **`trend30.evaluate_bars`** | 128.55 ms | **76.78 ms** | **−40.3%** |
| ├ `collapse_stubs`（`iterrows()` → groupby 聚合） | 41.61 | 11.12 | −73.3% |
| └ `linreg_quality`（逐 bar 循环调 OLS → 闭式解 + 滑动窗矩阵乘） | 35.94 | 2.27 | **−93.7%** |
| `main.py::_refresh_spot_vwap_cache`（全市场 5000 只 `iterrows` → 批量算式） | 391 ms | **2.4 ms** | **159.6×** |
| `add_indicators`（**对照，未改动**） | 34.97 | 37.25 | +6.5% ← 噪声带 |

对照组仅漂 +6.5%，故 −40.3% 可信。按 50 只池算，**每次全量标签刷新省 ~2.6 秒纯 CPU**。

**验证**：`collapse_stubs` 与 `linreg_quality` 在 400 只真实 30min 序列 + 13 个合成/边界用例上
**逐元素等价（含 NaN 模式），0 不符**；`tests/phase3/test_trend30.py` 14/14、
`test_trend30_permission.py` 4/4 通过（`test_gui_ob_30min.py` 的 4 项失败经 `git stash` 对拍
确认为**改动前既有**的数据依赖失败）。

### 三条铁律（本轮踩出来的，后续必守）

### ⚠️ 战略结论：CPU 不是这套系统的瓶颈

这是本轮最重要的判断，且与"CPU 是重点中的重点"的直觉相反：

1. **GUI 标签批算是 TTL 缓存的**：[`load_stock_tags_batch`](t_gui.py#L4655-L4658) 自带注释
   「GUI 每 10s 轮询 refresh_pb 时走**缓存即时返回**，避免 7-12s 的批量计算」，
   池子约 **50 只**。⇒ 真实 CPU ≈ 50 × ~7ms / 120s TTL ≈ **0.35s / 120s**，可忽略。
2. **那 7-12s 是逐股网络等待**（`_stock_tags_one` → `fetch_daily_kline` + `get_trend30`，每只票出网），
   不是 CPU。
3. **冻结栈里的 `_stock_tags_from_df 121` 是「线程数」不是「CPU」**——那些线程在**等网络**。
4. 与既有实测一致：memory 记录 GUI 进程 CPU 仅 **14%**、WebView2 6% ⇒「不是 CPU/GIL 问题，是在干等」。

⇒ **「卡顿」的主轴是 I/O 等待（逐股出网），不是 CPU。** 继续在 CPU 上挖，边际收益会越来越小
（本轮仅 −20.6% 的零头，上轮是 −40%）。若目标是"系统不再卡"，下一个该攻的是
**逐股网络取数的合并/缓存**，而不是更多 CPU 微优化。

### 测量工具的一处加固（噪声标尺）

本轮暴露一个方法学问题：机器上跑别的进程时，**未改动的函数也会「变慢」+60~105%**
（实测 `json_to_df` +98.4%、`add_indicators` +104.6%、`vwap.vectorized` +195.4%）
⇒ 拿绝对毫秒做跨日比较会得出**假结论**。

已在基准里加入 **`__canary__` 噪声标尺**（定长纯 Python 工作负载，结果恒定，只受机器负载影响），
报告新增「噪声×」列与**归一化表**（各项 ÷ 噪声×），且首末对比会标注「在噪声带内」。

⚠️ **局限**：canary 只能**向前**生效——加它之前的历史轮次无法回溯归一化。
**在机器有外部负载时，唯一可信的判据是「带对照项的背靠背 A/B」**（本轮即靠它定出 −20.6%）。

## 五之三、I/O 合并调查：**结论是不可行**（2026-10-11 续）

上节指出「卡顿主轴是逐股网络等待」，故本轮评估把逐股取数**合并**。**结论：不可行，且已有人踩过坑。**
先把成本量清楚（`_stock_tags_one` 分段，6 只小样本）：

| 阶段 | ms/只 | 占 | 交易日是否发生 |
|---|---|---|---|
| `fetch_daily_kline`（日线） | **480** | 61% | ✓ |
| `get_trend30`（tushare 30min） | **246** | 31% | ✓（30min slot 缓存内的首算） |
| `_live_quote_forming`（补当日 bar） | 48 | 6% | ✗ **仅当末根≠今日才触发**；交易日 `daily()` 已补当日 bar ⇒ 不触发 |
| `_stock_tags_from_df`（纯计算） | 8 | 1% | ✓ |

实测均值 **1609 ms/只**（含 GM 4s 超时；另一轮 782ms/只，方差极大）
⇒ 50 只 ≈ **13.4s 墙钟**，与冻结日志 `load_stock_tags_batch 12147ms` **精确吻合**。

**四条否掉「合并」的证据**：

1. **GM 批量通道在本机常态不可达时会整批返空**。实测：`daily()` 5 只全返 800 行
   （走腾讯兜底），而 `daily_many()` **一只都没返**（"GM 不可用，5 只非北交所码本轮无日线"）。
   ⇒ 换批量会让 GUI 在**掘金终端没开时全空**。
2. **批量 GM 调用会冻界面——团队已经踩过并记录**：[`t_gui.py:4742-4745`](t_gui.py#L4742-L4745)
   写着「900 → 200。GM SDK 里 pandas 由 list-of-dicts 拼表 + 逐码 groupby **会长时间持 GIL**，
   实测把 pywebview 主线程**饿死**（看门狗抓到主线程卡在 `evaluate_js`）」。**批量化在这里是反效果。**
3. **30min 本地缓存已陈旧 3 周**（末根 `2026-09-18`，mtime 09-20，今天 10-11）
   ⇒ `get_trend30` **不能**改读 `t_io/cache/tushare_mins/` 省掉 tushare——会产出错误趋势。
4. **腾讯日线无批量 K 线 API**；其磁盘缓存闸门是 `date == 今天`，跨日即失效（故周末每次都走网络）。

⇒ 交易日的标签批算 = `daily`（逐只网络）+ `trend30`（逐只 tushare），**两者都无法用代码消除**。
**要更快只能换数据源**（掘金终端常驻 / 有批量能力的授权源），不是改代码。

> ⚠️ 另注：`add_indicators`（~35ms/只）虽然 32% 花在 24 次列赋值上可批量优化，但它的调用方含
> [`execution/auto/gm_main.py:1617`](execution/auto/gm_main.py#L1617) —— **在交易路径内**。
> 收益（2~16%）与风险（go-live 前动交易引擎）不成比例，**不做**。
