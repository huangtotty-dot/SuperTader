## §1 建仓信号扫描 · 实时涨幅

**根因**：`web/app.js` 的 `load_quotes` 叠加路径**只搬了 `price`、把 `change_pct` 丢了**：

```js
state.quotes.forEach(x => pxMap[x.code] = x.price);          // ← change_pct 在这里被丢掉
pbRows.rows.forEach(r => { if (pxMap[r.code] != null) r.price = pxMap[r.code]; });
```

而建仓表的行来自扫描留痕 `position_builder_{date}.jsonl`，那份记录里**本来就没有涨跌幅**
（只有 `price`）⇒ 不叠加就**永远**不会有涨幅，不是"偶尔缺失"。

**修法**：抽出 `applyQuotesToPB(pb)`，一次搬 `{price, change_pct}` 两个字段。
⚠️ **必须两处都调**：① 10s 的 `load_quotes` 路径；② `refresh_pb` 回来的新 payload ——
后者会**整体替换** `state.payload.position_builder`，只改①的话涨幅会被下一次渲染洗掉
（本文件既有同类教训：技术标签曾因"覆盖再渲染"一会儿有一会儿无）。

**实测数据源**（`_load_quotes_build()`，真机）：`source=live`、52 只、**50/52 的 `change_pct` 非零**
⇒ 确实显示得出东西。覆盖范围 = 持仓 + `watchlist_buy` 候选股（正是建仓表扫的池），不在覆盖内的行显示 `—`。

## §2 选股猎手 · 个股实时涨幅

**根因**：数据**早在下发**（`t_gui.py` 的 `sector_stocks` 构造处就有
`"change_pct": round(float(d.get("涨跌幅", 0) or 0), 2)`），但**前端那一行压根没有涨幅列** ——
猎手个股行渲染的是 代码/名称/梯队/判定/得分/通过/日线阶段/5日线/**价**/技术标签/条件/理由，没有涨幅。

**修法**：在「价」格里**上下叠放**（价在上、涨幅在下），与建仓表**完全同款**。
不新增列：建仓表此前刚按 owner 要求从 19 列瘦到 16 列（见 memory），再插一列与那个方向相反；
而叠放是本文件既有的cell惯例（得分格下面带 `/上限🔒`、5日线格下面带 `−70`）。

**共用渲染器** `pctHtml(v, tip)`：两个面板一个口径（`>+0.05%` 红/`<-0.05%` 绿/其余灰）。
⚠️ **取不到显示 `—` 而不是 `0.00%`** —— 本仓踩过"把无数据画成平盘"的坑（盘前假当日根让
600362 误报破 5 日线），涨跌幅尤其不能猜。

> ### ⚠️ 后来 owner 实测发现这里**标错了口径**（已修，见 §7）
> 本节最初直接把 payload 里的 `change_pct` 当"实时涨幅"渲染 —— **错的**：
> 猎手 payload 是"跑扫描那一刻"的快照，可能隔了几天。owner 实测 300821 显示 **+20.01%**
> 而当天实时只有 **+5.83%**。§7 记录根因与修法。

## §3 选股猎手 · 二级板块（细分）得分

**根因**（最有意思的一条）：二级组头**有**"均分"，但它取的是 **`s.score`＝韭研 D1–D11 总得分**
（全池均值仅 **~0.8**，pipeline 自报"得分范围 0~16, 平均 0.8"）⇒ 组头显示 **「均分 1」**，
而它正下方那一列「得分」是**建仓综合得分（0~100）**。**两个数根本不是同一个东西**，
所以看起来就是"二级板块没有得分"。

```js
const gAvg = Math.round(gs.reduce((a, s) => a + (s.score || 0), 0) / gs.length);   // ← 韭研总分
```

**修法**：改取**行内同一个 `build_score`**（建仓综合得分，与下方「得分」列同源）取均值，
并显式区分三态：算了→`均分 <b>85</b>`（若只算了一部分，附 `（2/3只已算）`）；
还没算到→`均分 ⏳更新中`；算了但无值→`均分 —`。

⚠️ 踩到的坑：第一版用 `s._buildMissing` 判断"还没算到"，但那是 **`hunterRow()` 渲染时才置位**的，
而组头在 `gs.map(hunterRow)` **之前**算 ⇒ 首帧读到 stale/undefined。改为用与 `hunterRow`
**完全相同的谓词**（`!_buildReady && s.build_verdict === undefined`）直接判。

## §4 顺带发现：`fmt()` 不是定宽

`fmt(v, d)` 用的是 `toLocaleString({maximumFractionDigits: d})` —— **"最多 d 位"，不是固定 d 位**：

```js
fmt(3.5, 2) === "3.5"    // 不是 "3.50"
fmt(0, 2)   === "0"      // 不是 "0.00"
```

涨跌幅一列用它会打出 `+3.5%` / `+0%`，**数字对不齐，且 0 与 0.00 看起来像两种东西**
⇒ `pctHtml` 内改用 `n.toFixed(2)`。
（既有的指数板 `pctTxt` 也用 `fmt(pct,2)`，同样有这个现象；不在本次范围，未动。）

## §10 owner 追问：「我点击扫描是不是根据最新价格进行的？」→ **盘中以前不是，这是真 bug**（已修）

owner 的直觉是对的。答案是**分两半**：

### 10.1 机制上本来是会的

`fetch_for_date(codes, date)` 里有专门一步补当日价：

```python
if str(target_date_str) == now.strftime("%Y-%m-%d"):
    _sn = _TP().snapshot_auction(list(dict.fromkeys(_c6map.values())))
    for _c, _v in _sn.items():
        if _v.get("ts_date") == str(target_date_str):
            self._live_snap[_c] = _v
    print(f"  [LIVE] 盘中快照 patch {len(self._live_snap)}/{len(_c6map)} 只")
```

用 4 只试 ⇒ `[LIVE] 盘中快照 patch 4/4 只`，`数据日期=2026-10-12`、`现价=17.94` ⇒ **看着完全正常**。

### 10.2 但整池调不通 —— **静默返空**

`snapshot_auction` 把**全部 symbol 拼进一个 URL**，而 URL 一长就被 qt.gtimg.cn **静默拒绝**
（返回空 body，函数里 `except: pass` ⇒ 表现为空 dict，调用方看不出错）。实测悬崖：

| n | URL≈ | 耗时 | 返回 |
|---|---|---|---|
| 800 | 12000 字符 | 0.87s | **800** |
| **1000** | **15000 字符** | 0.19s | **0** ← 空 |
| 5382 | 48000 字符 | 0.24s | **0** ← 空 |

而那个 live patch 传的是**整池**（猎手池 1200~1500 只）⇒ **常年 patch 到 0 只** ⇒
扫描的价/涨跌幅只能取日线历史，而**日线盘中不含当日 bar** ⇒ **整块面板退回上一交易日**。

⇒ 这才是 owner 看到 300821 显示 **+20.01%（10-09 涨停那天）** 而当天只有 **+4.6%** 的**真因**：

## §11 owner：「还是更新太慢」——继续优化（2026-10-12）

先确认 §8 的修复**确实生效了**：GUI 于 **13:33:35** 重启（晚于 13:28 的改动），
`gui_slow_calls.log` 里 `load_quotes_for` 从 **8639ms / 8496ms → 802ms / 1716ms** ✓。

剩下的慢是**另外三个原因**（都不是超时）：

### 11.1 串行顺序错了：先白等标签 4~7 秒

```js
await loadSectorTags(category);     // ← 实测 4.5s（冷启 7.3s）
applySectorTags(tbody, category);
loadSectorQuotes(category);         // ← 行情要等它跑完才开始
```

标签与行情**互不依赖**，却排成一前一后 ⇒ 价格出现的等待 = 标签 + 行情。
→ 改成**并发**：`loadHunterQuotes()` 提到 `await loadSectorTags(...)` **之前**。

### 11.2 N 个展开板块 = N 次调用

原设计是"每个板块各发一次"。而这个 GUI **单次 js_api 基线就有 ~1s**
（同日日志：`load_console 985ms` / `refresh_pb 929ms` / `load_live 1982ms`），
前端在飞上限 6 ⇒ 展开 5 个板块就是 5 次并发互相排队，**越展开越慢**。
→ 改成**一次请求覆盖全部展开板块**：`_allRenderedHunterCodes()` 取并集去重，
外加**全局单飞 + 全局 TTL**（原先是每板块各一套状态）。

### 11.3 我自己的一个 bug：`_QUOTES_FOR_MAX = 120` 会静默截断

多个板块展开时并集会超 120，**排在 120 之后的股票永远显示 ⏳**（静默）。
→ 上限提到 **400**，并改走 §10 的**分块**版 `snapshot_auction_many`。

### 11.4 实测

| 请求规模 | 耗时 |
|---|---|
| 40 / 120 只（1 块） | 0.24~0.33s |
| 250 / 400 只（2 块） | 0.61~0.65s（偶发一次 3.63s） |

> ⚠️ **技术细节**：`urlopen(timeout=N)` 是**每个 socket 操作**的超时，**不是**墙钟总时限 ——
> 响应若"断续抵达"可以远超 N（这解释了为什么 timeout=8 的调用实测能跑到 8.33s）。
> 所以 8s→3s 是**降低**常见挂死的等待，不是把单次调用硬封在 3s。

### 11.5 见效方式

- 前端（`web/app.js`）：**刷新页面**即可
- 后端（`t_gui.py` 的 `_QUOTES_FOR_MAX` / 分块）：**需重启 GUI**

冒烟测试 **ALL PASS**；phase3 **492 项**、stage0_2 **59 项**，仅剩既有失败。

## §13 视觉中国误报「破5日线」——**同类第 3 次**（2026-10-12，已修）

owner：「视觉中国我查看同花顺已经是站上5日线，但显示的是破5日线」。

### 13.1 数据对照（一眼看出是缓存缺当日 bar）

```
日线缓存 000681 末根 = 2026-10-09 close=14.98（文件写于 10-09 11:12）
  用缓存末 5 根算 MA5 = 15.482 → 14.98 < 15.482 ⇒ 报「破5日线」（= 10-09 那天的事实）
当日实时            = 16.69（昨收 16.14, +3.41%）
  含当日算 MA5 = 15.700 → 16.69 ≥ 15.700 ⇒ 实为「站上」 ✓（同花顺对）
```

⇒ 标签是拿**缺当日 bar 的缓存**算的。而猎手本来**应该**把当日实时 bar 回写进这个共享缓存
（`_hunter_build_conformance` 的注释就写着"该缓存已由猎手本轮拉取**回写当日实时 bar**"）。

### 13.2 根因：一个性能优化把回写**悄悄**削掉了

`fetch_one` 里那段"当日回写共享缓存"被提交 **a13a9b5**（「取数改走本地缓存 —— 从 ~280s 到 ~60s」）
引入的 `_bulk_from_cache` 干掉了：

```python
_df = _cc.load_daily_display(_c6)          # 读本地缓存（新鲜度闸 = 12 个自然日！）
if _df is not None and not _df.empty:
    self._bulk_kline[_c6] = _df
    self._bulk_from_cache.add(_c6)          # ← 无条件当作「值未变，省去回写 merge」
```

`load_daily_display` 允许**最多 12 天**陈旧 ⇒ "末根停在上一交易日"（只差 3 天）的缓存
被当成"值未变" ⇒ **跳过回写** ⇒ 共享缓存**永远**补不上当日 bar
⇒ 零网络的消费端（**技术标签** / 建仓符合度）一直按陈旧序列算。

### 13.3 修法（两处，都要）

① `_bulk_from_cache.add` **只在缓存末根 == 目标日**时才加（保住优化：真有当日 bar 才省回写）；
② 回写条件加"手上确实有当日 bar"（`df 末根 == 目标日`），避免无谓 I/O。

### 13.4 验证

- **缓存层**：回写后 `000681` 末根 `2026-10-09 14.98` → **`2026-10-12 16.69`**，
  MA5 15.482 → **15.700**，判定 **破位 → 站上** ✓
- **走猎手真正用的那条路**（`load_stock_tags_batch(['000681'], offline=True)`）：
  `{"price": 16.69, "trend_src": "30min", "tags": [震荡, 箱体内部]}` ⇒
  **"破5日线"消失** ✓（今天既没破、也没"刚站上"跃迁，故两个标签都不出现 —— 原来那个确实是假报）
- 回归守卫 `tests/phase3/test_hunter_daily_cache_writeback.py` **4 项**
  （源码守卫，与 `TestT6GmMainStatics` 同做法，因该段要真实网络才能跑通）

### 13.5 代价

单只回写实测 **20ms** ⇒ 全池 1400 只约 **+28s**。**但每只每天只发生一次**：
第一次盘中扫描把当日 bar 写进缓存后，后续扫描的缓存已含当日 ⇒ 走豁免 ⇒ 不再写。
（代价：当天那根 intraday bar 的 close 停在**第一次扫描时**的价 —— 与改动前的既有新鲜度同级。）

### 13.6 ⚠️ 为什么 §2 的新鲜度巡检**没能先抓到**

巡检的日线阈值是 `MAX_DISPLAY_GAP_DAYS = 12`（对齐**展示**口径，要能跨长假），
而"末根停在上一个交易日"只有 **3 天** ⇒ 判为**新鲜** ⇒ 不报。
⇒ **对"要用最新一根算均线"的消费端，判据应是『是不是今天』，不是『多久没更新』。**
（已把这个认知钉进 `test_hunter_daily_cache_writeback.py::TestFreshnessGapGuardsTheSameClass`。
要不要给巡检加一条"末根非最新交易日的只数"（用池内最大末根日期自校准，不需要交易日历），
owner 说了就加。）

> 本类缺陷本仓**已第 3 次**：600362×2（payload 停滞 / 补 forming bar 把昨收重复计入）+ 视觉中国。
> 记忆里那条至今有效：**凡用最新一根算均线，都要先问"这根真的成交过吗 / 是今天的吗"。**
