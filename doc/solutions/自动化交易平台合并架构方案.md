# 自动化交易平台合并架构方案

> 版本：V1.0（2026-08-28）
> 状态：**待评审**（含 §9 待决策点，需用户拍板后进入实施）
> 勘察依据：superTrader 全库 + goldminer 项目（`c:\Users\Lenovo\.goldminer3\projects\e8bb1f4d-87ce-11f1-97f7-98fa9b8df5e7\`）双侧代码勘察，关键结论附文件行号

## 1. 背景与目标

superTrader 目前是**人工辅助**做T平台：系统出信号 → 飞书推送 → 人工下单 → 收盘按虚拟成交净额回写持仓。goldminer 是**自动化**模拟盘做T平台：掘金 SDK 驱动，信号→风控→市价单→成交回报全自动，2026-07-27 上线至今每日实盘（模拟）运行。

用户目标：
1. goldminer 自动化平台**合并进** superTrader；
2. 四个同源：**GUI 同源、数据获取同源（统一走掘金量化数据接口）、做T引擎同源、加仓建仓逻辑同源**；
3. goldminer 侧的**止盈止损及其他执行管理保持独立**。

## 2. 现状勘察摘要

### 2.1 两系统对照

| 维度 | superTrader（人工辅助） | goldminer（自动化） |
|------|------------------------|---------------------|
| 入口/进程 | `main.py` 盯盘主循环 + 子进程 `t_gui.py`（pywebview GUI） | 掘金终端内策略 `main.py`（2309 行，唯一耦合 gm.api）+ 常驻 `gm_bridge/watcher.py`（事件→飞书） |
| 调度 | 顺序轮询（每轮间隔 15s）+ 时段门控 | 掘金 60s bar 订阅推送驱动 |
| 数据源 | 腾讯行情直连（~10 处内联调用，WAF 多主机兜底散落各处）+ akshare/tushare 备源 | gm.api：`subscribe(60s)` + `history_n`（60s/日线），API 面极小 |
| 做T引擎 | `core/signal_engine.py` SignalEngine（评分+门控） | `signals/engine.py`（~40 特征 sigmoid 打分 + RiskManager 一票否决） |
| 建仓加仓 | `core/position_builder.py` + `core/timing_gate.py`（regime 门控/追强/抄底/否决因子，1/3 分批建议） | `signals/position_builder.py`（同步自 superTrader 但有已知口径差）+ 建仓闸链（池闸→MA5 禁令→趋势闸→槽位闸→双通道闸） |
| 成交真源 | 人工跟单 + VIRTUAL_TRADES 虚拟记账 + 收盘净额回写（t_qty 只减不增不变量） | `on_order_status` 真实成交回报驱动台账 |
| 止盈止损 | 无（人工管理） | P0-P6 卖出通道 + `_sell_arbiter` 统一仲裁 + `sell_state.json` 跨日状态（**保持独立的部分**） |
| GUI | pywebview 看板（~70 个 Api 方法，多数只读落盘文件） | 无做T GUI（仅 tkinter 仓位配比小工具，与引擎零耦合） |
| 持仓池 | watchlist_buy.json 41 只监控池 + holdings.json 4 只持仓 | 17 票候选硬编码 + 5 票目标底仓，槽位制 ≤4 票同持 |

### 2.2 关键发现（决定方案形态）

1. **两系统本是同一份代码（E:\06_T）的两个演化分支**（goldminer 侧 `signals/engine.py:5`、`position_sizer.py:6`、`data/indicators.py:5`、`analysis/index_regime.py:5` 均注明移植来源）——合并是"回合"，不是"对接"。
2. **goldminer 信号/指标/建仓层是纯函数、零 gm 依赖**（`signals/`、`analysis/`、`data/` 不 import gm），时间由 `SIM_NOW` 注入——可整体搬迁。
3. **superTrader 做T引擎的耦合方式特殊**：`main.py:73-99` 把 13 个模块 exec 进同一命名空间，SignalEngine 依赖共享可变全局（VIRTUAL_TRADES/HOLDINGS 等靠对象引用同一性工作）——这是引擎同源改造的最大卡点。
4. **已有现成事件总线**：goldminer 的 `runtime/bridge/` jsonl（signal/order/fill/reject/risk/heartbeat 七类事件 + KILL_SWITCH），schema 稳定、append-only。superTrader 侧 `t_io/gm_bridge/` 只剩 08-06 前冻结历史，无活消费。
5. **superTrader 数据层无抽象**：腾讯 URL/WAF 兜底/代理清除逻辑复制散落在 ≥10 个文件，切数据源必须先建抽象层。
6. **两分支已分叉演化 5 周**，同名模块各自打过实战补丁（goldminer 有 WP-B07/B14/B15 等系列修复；superTrader 有 C-1~C-5/方案A/否决因子等），逐文件语义对齐是主要工作量。

## 3. 可行性评估

**结论：可行，且比预期乐观。** 四个同源中三个有现成基础：

| 同源项 | 难度 | 依据 |
|--------|------|------|
| GUI 同源 | **低** | goldminer 无做T GUI，无资产冲突；t_gui 本就是"读落盘文件"的看板，加自动盘页即可 |
| 数据获取同源 | **中** | gm 数据 API 面小（history_n 两类），但需要新建 Provider 抽象 + 收敛 superTrader 侧 10 处调用点 + 口径映射（§5.1） |
| 做T引擎同源 | **高** | 两分支同名引擎已分叉 5 周，需逐补丁语义对齐；superTrader 侧 exec 共享命名空间需改显式注入 |
| 加仓建仓同源 | **中高** | 已知口径差有文档记录（箱体窗口/量能冻结/预热期），属"同名不同行为"陷阱，需逐项裁决 |
| 止盈止损独立 | **天然满足** | 全部集中在 goldminer `main.py` 执行层，以 Signal 对象 + 事件桥为界即可划清 |

**前置验证项（开工前必做）**：掘金 token 的数据接口配额/权限实测（history_n 日线 800 天 × 41+ 只的拉取频率限制、盘中 60s bar 订阅的标的数上限）——这决定数据同源是"gm 主用"还是"gm 主用 + 腾讯兜底降级"。

## 5. 专项设计

### 5.1 数据获取同源（统一掘金接口）

**新建 `core/market_data/` 抽象层**，四个方法契约：

| 方法 | 返回契约 | 现 superTrader 调用点（收敛目标） |
|------|---------|----------------------------------|
| `daily(code, days=800)` | DataFrame[date,open,high,low,close,volume]，**前复权** | position_builder.py:302、timing_gate.py:62、index_regime.py:691、market_review.py:159 等 |
| `minute(code, date)` | DataFrame[time,open,high,low,close,volume,amount]，volume 单位**手** | data_fetcher.py:647、position_builder.py:180、index_regime_intraday.py:154 |
| `snapshot(codes)` | 实时价/VWAP | position_builder.py:264、t_gui.py:320/492/2429、auction_analyzer.py:313 |
| `index_daily/index_minute` | 指数专用（sh000001） | timing_gate、index_regime* |

**口径映射（codec.py）——必须显式处理的三个坑**：
- **代码格式**：GM `SHSE.600481` ↔ 内部 `600481` ↔ 多账户后缀 `600481_A/_B`（superTrader 特有，GM 侧无对应物，映射时保留后缀语义）；
- **成交量单位**：腾讯分钟 volume=手（VWAP 计算内嵌 ×100，data_fetcher.py:889-896），GM=股——统一为"手"或全部改"股"并逐一改系数，**建议统一为股，腾讯侧 ×100 收敛到 provider 内**；
- **复权**：superTrader 全部指标假设前复权日线；GM history 默认不复权——provider 内强制 `adjust=ADJUST_PREV`。

**降级策略**：GmProvider 主用，TencentProvider 兜底（gm 配额/终端不可用时），缓存契约不变（`t_io/cache/daily_kline/` 格式保持，迁移期双写对照一周）。

### 5.2 做T引擎同源

**核心改造：exec 共享命名空间 → 显式依赖注入。**

superTrader 侧 `main.py:73-99` 的 exec 模式是引擎抽取的唯一硬卡点。改造方案：

```python
# core/signal_engine.py 目标形态
@dataclass
class EngineContext:          # 显式注入，替代共享全局
    holdings: dict
    virtual_trades: dict
    minute_fetch_status: dict
    t_mode: str
    now: Callable[[], datetime]   # 时间注入（对齐 goldminer SIM_NOW 契约，保回测可重现性）
    append_jsonl: Callable
    fetch_minute_bar: Callable    # 来自 market_data provider

class SignalEngine:
    def __init__(self, ctx: EngineContext, params: dict): ...
```

**分支合并策略**（两分支已分叉 5 周，逐文件语义对齐）：
1. 以 superTrader 现版本为基线（它有今日刚验证的否决因子/门控修复）；
2. 逐条审查 goldminer 侧 WP-B 系列补丁（B07 回补价格记忆、B14/B15/B18/B19/B22 等），逐条裁决：合入 / 仅自动侧保留（执行相关）/ 已过时放弃；
3. 每条补丁附双系统回测对照（superTrader `scripts/harness_backtest.py` + goldminer `replay_wp*.py` 双跑）。

**双消费接线**：引擎输出 Signal 后分叉——manual 链路走 `notify()` 飞书推送（现状），auto 链路走闸链→下单适配器。Signal dataclass + sizing_advice JSONL 已是机器可消费格式，分叉点干净。

### 5.3 加仓建仓同源

superTrader 的 `position_builder + timing_gate` 已是单一实现且今日刚完成一致性修复，**作为合并基线**。goldminer 侧 `signals/position_builder.py` 的已知口径差逐项裁决：

| 口径差 | superTrader | goldminer | 裁决建议 |
|--------|------------|-----------|---------|
| 箱体窗口 | 150 日/30 窗 | 60 日/24 窗 | 取 superTrader（样本更厚），goldminer 历史结论用参数重验 |
| 量能 | 实时量 | T-1 冻结量（放量滞后一日） | 取实时量，auto 侧注意 bar 驱动下的"当前 bar 未完成"语义 |
| 冰点预热 | 需 ~25 分钟 5m 数据 | 同 | 统一预热策略 + 盘前预取（gm history_n 60s×240 可覆盖） |

goldminer 特有的建仓闸链（池闸/MA5 禁令/趋势闸/槽位闸，main.py:1359-1505）属于**执行侧风控**，归入 §5.5 独立边界，不进公共判定层。

### 5.4 GUI 同源

t_gui 看板本就该就是"读落盘文件"的架构，扩展成本低：

1. **新增"自动盘"页**：读 `t_io/bridge/` 事件流（signal/order/fill/reject/risk）+ heartbeat（positions/cash/index_regime），展示自动侧持仓/当日成交/拒单/风控事件；KILL_SWITCH 状态做醒目横幅；
2. **现有页升级**：持仓/做T页同时显示人工侧（holdings.json）与自动侧（bridge positions）两个台账，标注来源；
3. **晨间 reconcile 重新定位**：人工侧持仓真源维持人工截图；自动侧持仓真源 = GM 成交回报（见 §6）；
4. GUI 直连网络的 4 处调用（t_gui.py:320/492/2429/3437）改走 market_data provider，完成数据同源的最后一块。

### 5.5 独立边界（止盈止损与执行管理）

**明确不动**的部分（goldminer 迁入 `execution/auto/` 后保持独立演化）：
- P0-P6 卖出通道（MA5_EXIT/PANIC_SELL/TRAIL_SELL/TREND_EXIT/TARGET_SELL/TAIL）与 `_sell_arbiter` 仲裁；
- `sell_state.json` 跨日状态（pos_key 持仓指纹校验）；
- 仓位资金管理（总权益预算制/单票 80% 上限/KILL_SWITCH）；
- watcher.py 飞书推送链路（事件推送/去重/限流假定现有 schema——**合并后扩展事件命名空间，不改现有字段**）。

**边界接缝**：auto 侧从公共层拿 Signal 和数据，执行/止盈止损/台账自己管。跨边界契约只有两个：Signal 对象、bridge 事件。

## 6. 通信与状态契约

1. **事件桥升级为主总线**：`runtime/bridge/` 迁入 `t_io/bridge/`，schema 沿用。superTrader 侧新增写者时的纪律：**jsonl append 无锁，单文件单写者**——events 由 auto 侧写，manual 侧如要写信号事件用独立文件（如 `manual_signals_{date}.jsonl`）。
2. **持仓真源分工**：自动侧 = GM 成交回报（唯一真源）；人工侧 = 人工 reconcile + 收盘净额回写（现状）；VIRTUAL_TRADES 降级为影子对照。GUI 并表展示，总账由 portfolio_config 账户维度区分（衔接 doc/solutions/accounts_integration_plan.md 的多账户设计）。
3. **凭证安全（必须处理）**：goldminer `main.py:2309` 掘金 token 明文且已入 git——合并时移到 gitignored 配置文件（参照 superTrader `t_io/state/config.json` 模式），并**换发 token**（已入库的视为泄露）。

## 8. 风险清单与缓解

| # | 风险 | 等级 | 缓解 |
|---|------|------|------|
| 1 | gm SDK 数据配额不够支撑 41+ 只 × 800 天日线 + 盘中订阅 | **高** | P0 先实测；腾讯 provider 保留为兜底降级 |
| 2 | exec 共享命名空间改造引入隐性语义变化（对象引用同一性破坏） | **高** | EngineContext 显式注入后，用同一历史日逐 bar 回放对照新旧引擎输出，差异必须为 0 |

| 5 | bridge jsonl 双写者交错 / watcher 对 schema 的假定被破 | 中 | 单文件单写者纪律；事件只扩展命名空间不改现有字段 |
| 6 | sell_state.json pos_key 指纹对持仓源敏感，迁移后跨日状态静默作废 | 中 | 迁移日显式重置 sell_state 并记录；P5 观察期逐日验证 |
| 7 | 掘金 token 已泄露在 git 历史 | **高**（安全） | P0 换发 token + 配置化 + git 历史清洗（或至少确认仓库私有） |
| 8 | 掘金终端/模拟盘环境与 superTrader 运行时段冲突（终端需常驻） | 低 | auto 链路独立于 main.py 进程，GUI 只读 bridge 文件，天然解耦 |

## 9. 待决策点（需用户拍板）

1. **仓库形态**：物理合并进 superTrader 单一仓库（推荐，本方案按此设计）vs 双仓库 + 共享包？
2. **数据主源**：P0 实测后定——gm 配额够 → gm 主用 + 腾讯兜底；不够 → 腾讯主用 + gm 仅供 auto 侧，"同源"降级为"同抽象层不同源"（需重新评估意义）。

5. **分叉补丁冻结令**：P2 期间两分支是否接受冻结新功能补丁（只修线上事故）？

## 10. 总体工作量评估

净工作量约 **8-12 个工作日**（P0-P4）+ 2 周并行观察（P5）。最大不确定项是 P2 引擎语义对齐（5 周分叉的补丁归账）。建议按阶段推进，每阶段验收后再进下一阶段，**不建议大爆炸式一次性合并**。
